# 像素怪獸養成對戰機：Godot 開發 Prompt

使用方式：將下方「Prompt 開始」至「Prompt 結束」貼給具備 Godot 開發能力的 AI。預設採用原生手機 App、直式畫面、單人開發規模。數值是首輪原型的設計起點，需透過實測調整。

## Prompt 開始

> **專案決策更新（2026-09-23）：** 本 Prompt 保留最初需求與 Stage A 實作背景。後續開發已改為 iOS 優先的放置型遊戲：自然時間可以完成所有孵化與進化；Core Motion 步數與 Apple 健康 `HKWorkout` 只提供有上限的選配加速，不影響內容或能力上限。下方「走路孵化」、500／2,000／5,000 步門檻和三次訓練成熟門檻不再是目標規格。實作請以[放置成長規格](../../prototypes/pixel-monster/docs/IDLE-GROWTH.md)、[iOS 技術架構](../../prototypes/pixel-monster/docs/IOS-ARCHITECTURE.md)與[目前實作契約](../../prototypes/pixel-monster/CONTRACT.md)為準。

你是一位熟悉 Godot、手機原生功能串接、像素美術、電子寵物養成與遊戲數值設計的資深遊戲開發者。請協助我製作一款能在 iOS 與 Android 手機遊玩的「像素怪獸養成對戰機」，暫名《口袋怪獸日記》。請使用繁體中文說明，程式識別字使用英文。

我要能逐步執行、測試、擴充的遊戲專案。請先提出精簡設計與開發順序，再開始實作當前階段；不要只交付概念、靜態畫面或互不連接的程式片段。

**1. 遊戲定位與體驗**

- 靈感來自掌上型怪獸對打機：照顧、觀察、培育、分歧進化與短回合對戰。
- 怪獸、美術、名稱、音樂與介面採用原創設計，保留復古電子寵物的手感。
- 核心循環：取得蛋 → 走路孵化 → 餵食與照顧 → 訓練 → 戰鬥 → 分歧進化 → 收藏成長紀錄、開始下一輪培育。
- 主畫面是一隻生活在小房間的怪獸；玩家能從動作與表情看出牠的需求。
- 每次遊玩約 1～3 分鐘；單次照顧約 5～15 秒，訓練約 15～30 秒，戰鬥約 20～40 秒。
- 同時養育一隻怪獸或孵化一顆蛋。首版不加入大地圖、自由移動、大量貨幣或抽卡系統。
- 養成選擇要影響能力與進化，但忙碌一天不應導致永久死亡。長期未照顧可進入虛弱或休眠狀態，回來後能恢復。
- 以陪伴感為主：餵食會開心、疲倦會打哈欠、戰敗會失落、被照顧會親近玩家。

**2. 七項核心功能**

| 功能 | 操作與效果 | 視覺／音效回饋 |
| --- | --- | --- |
| 體重計 Scale | 開啟狀態頁，查看名字、階段、年齡、體重、飽食度、心情、精力、健康、清潔度、攻防敏、戰績與進化線索。體重有物種／階段對應的理想範圍，不是越重越強。 | 怪獸跳上體重計，數字跳動後停下，播放短提示音。 |
| 食物 Meat | 提供正餐與點心。正餐增加飽食度與體重；點心少量增加飽食度、較多提升心情。接近飽食上限時拒食並提示，避免連點無限增益。 | 食物逐口消失、咀嚼動作、飽足表情。 |
| 訓練 Training | 可選力量、防禦、敏捷；MVP 用同一套單指時機判定小遊戲承載三種訓練。消耗精力、略降體重，增加對應成長值。每個成長階段有可見上限。 | 普通／良好／完美判定、打擊特效、成長值增加。 |
| 戰鬥 Fighting | 首版與 NPC 進行短回合戰鬥；之後加入好友非同步對戰。使用攻擊、防禦、敏捷、技能、培育結果與有限隨機性。 | 出招、閃避、受擊、血量變化、勝敗表情與可跳過的戰報。 |
| 廁所 Toilet | 餵食後排入排泄事件，房間會出現便便。點擊清理恢復清潔度；堆積過久會降低心情並影響健康。 | 便便消失、清潔粒子、怪獸開心跳動。 |
| 燈光 Lights | 可開燈／關燈，提供可調整的作息與自動關燈選项。入睡需依作息或疲勞狀態判定，關燈不是立即回滿精力；睡眠恢復按時間計算。睡眠中避免頻繁需求警報。 | 畫面轉暗、閉眼呼吸、睡眠符號、柔和音效。 |
| 繃帶 Bandage | 呈現受傷與生病狀態，提供對應療護，限制連續使用。受傷影響戰鬥，生病降低活動能力；恢復必須有清楚倒數或條件。 | 包紮／療護動畫、狀態圖示改變、逐步恢復。 |

請定義每項操作的前置條件、數值效果、冷卻、動畫、失敗提示，以及對後續進化的影響。任何按鈕停用時都要說明原因。

**3. 數值、狀態與離線照顧**

- 飽食度、心情、精力、健康、清潔度採 0～100，統一為數值越高狀態越好。
- 分開設計長期戰鬥能力、當場戰鬥 HP、養成健康值與精力，避免一次戰敗直接造成寵物死亡。
- 分開儲存目前行為與持續狀態；例如怪獸可以同時「睡眠中」與「受傷」，不要用單一 enum 排斥所有組合。
- 飽食度與精力隨時間變化，健康問題來自持續未處理的需求。照顧失誤以「一個需求事件超過寬限期」記錄一次，不可每幀或每分鐘重複累計。
- 起始照顧寬限期可設 2 小時，睡眠時段凍結相關失誤計算。所有數值都放入可調整設定。
- App 回到前景時，依最後結算時間推進狀態，不依賴 Godot 在背景持續執行。先訂出睡眠、飢餓、排泄與疾病事件的順序，避免一次套用總扣分造成矛盾。
- 離線需求衰減暫定最多結算 12 小時，超過後進入保護性休眠；年齡、進化計時與步數同步使用各自規則，不能一起套用這個上限。
- 保存 UTC 時間；顯示作息與日曆時使用玩家時區。裝置時間倒退不得產生負數狀態、重複獎勵或免費成長。離線存檔不宣稱具有完整防作弊能力。

**4. 步行孵化：核心差異化功能**

- 新手蛋暫定 500 步、普通蛋 2,000 步、特殊蛋 5,000 步；數值可配置，特殊蛋不必具有更強戰鬥能力。
- 只計入蛋開始孵化之後的合格步數，不得把玩家當日早先走過的全部步數直接灌入新蛋。
- 顯示「本顆蛋已累積／需求步數」、同步狀態與最後同步時間。當日步數和孵化進度分開呈現。
- 孵化到 25%、50%、75%、100% 時，依序出現晃動、裂紋、光效、破殼。達標後只產生一次怪獸並存檔，再播放可重看的演出。
- 遊戲關閉期間，由可用的系統／健康資料來源記錄步數；再次開啟時補讀。不要讓使用者必須一直亮著螢幕，也不要用 GPS 距離估算取代本需求。
- 同一時間區間不得因重新整理、重開 App、延遲同步或切換來源而重複入帳。設計持久化的步數結算紀錄，支援重查近期區間與差額結算，處理健康來源晚到的資料。
- 跨日不可重置同一顆蛋的已累積進度。手機重啟造成感測器累積值歸零時，要重建基準，不得出現負值或暴增。
- 同一時間區間指定一個結算來源，不能把 Health Connect 與原始感測器的相同步數相加。未完整覆蓋的區間要顯示狀態，不得默默當成已同步。
- 超過目前蛋門檻的餘額不轉入下一顆尚未開始孵化的蛋。孵化開始、步數結算與孵化完成都需可重入且不重複發獎。
- 未授權、裝置不支援或無步數來源時，提供「時間孵化」替代模式，例如 24 小時，不把未取得資料顯示成確定的 0 步。
- 開發版提供模擬增加 100／1,000 步、拒絕權限、延遲同步、重複回傳、手機重啟等測試操作。模擬來源要明確標示，正式版不可出現增加假步數按鈕。

**5. iOS／Android 步數實作要求**

使用 Godot 處理遊戲與畫面，以原生外掛處理平台步數 API；不要假設 GDScript 本身可以直接讀取手機健康資料。

- iOS：優先採 Core Motion 的 CMPedometer，檢查計步支援與授權狀態，配置 NSMotionUsageDescription，以原生橋接提供區間查詢及前景更新。歷史回補需遵守 API 可讀取範圍；目前文件為最近七天，不承諾無限期補記。首版範圍是手機計步，不假設包含 Apple Watch 的所有步數。
- Android：優先評估以 Kotlin 原生外掛讀取 Health Connect 的步數聚合結果，處理 READ_STEPS、服務可用性與來源狀態。使用聚合 API 避免多來源逐筆相加。
- Android 的 Health Connect 不可被假設成所有手機預設都有完整步數：支援 Android 14 與 SDK Extension 20 以上的裝置具有特定內建計步能力；其他情境需確認是否有實際寫入來源。請按實際目標版本核對官方文件與實機行為。
- 若加入 TYPE_STEP_COUNTER，需處理 Android 10 以上的 ACTIVITY_RECOGNITION 權限、感測器是否存在、重啟歸零與生命週期限制。此來源不是完整的歷史步數資料庫，不保證 App 被終止後仍能回補所有步數。
- 首版在 App 回到前景時查詢歷史資料即可；不要把「系統背景記步」與「本 App 背景查詢」混為一談，也不要為此要求遊戲常駐背景。
- 桌面採 MockStepProvider。平台未接好時仍可測試養成，但完成報告必須清楚列出「模擬通過／原生未驗證」。
- 定義自己的 StepProvider 介面，包含能力檢查、權限、時間區間查詢、回傳來源與覆蓋範圍、錯誤狀態。具體函式簽名由你設計，需清楚區分自訂介面與官方 API。
- 原生回呼安全地回到 Godot 主執行緒後才更新節點或 UI，避免離開畫面後舊回呼覆蓋新狀態。
- 選定並固定實際使用的 Godot 4.x 穩定版、原生外掛與 SDK 版本，查官方文件驗證相容性。不能捏造外掛名稱或宣稱未編譯、未實機驗證的功能已完成。

**6. 分歧進化與收集**

- 初始內容：1 種蛋、1 種幼年體、1 種成長體、3 種成熟體。三種成熟體分別偏力量、防禦與敏捷，輪廓及動作也要不同。
- 進化條件包含階段時間、訓練傾向、照顧品質、睡眠紀錄與戰鬥經驗。走路主要推動孵化與少量陪伴回饋，不直接提供無上限攻擊力。
- 起始門檻可設幼年體 2 小時進入成長體、成長體至少 24 小時且完成 3 次訓練後進入成熟體。開發版提供快轉，正式版使用真實時間。
- 成熟體先按最高訓練傾向選擇分支；同分時採公開且固定的規則。照顧品質與戰鬥經驗可影響分支內的有限能力修正，不讓失誤直接永久鎖死所有進化。
- 請交付完整的進化條件表、判定優先序、未達標行為、預設路徑與範例；每個條件都要能由存檔中的資料重算。
- 顯示模糊但有用的線索，如「牠最近特別喜歡力量訓練」，進化後再揭露達成紀錄。
- 進化播放剪影、閃光、變形與新動作展示，且只能結算一次。
- 成熟後可選擇將怪獸保存到收藏冊，再培育新蛋；保存個體能力與培育歷史，不只是一張已解鎖圖示。好友戰鬥階段可選擇已收藏的成熟體。

**7. 戰鬥與好友對戰**

- MVP 使用 3 名固定 NPC，難度逐步增加。採回合自動戰鬥，戰前可選均衡／強攻／防守方針，每種方針有明確取捨。
- 每隻怪獸有普通攻擊與一個代表技能；請提供簡單可解釋的傷害、命中、先後手與技能觸發公式。
- 能力差距應有感，隨機性應受限。設定回合上限與平手規則；戰敗仍有有限回饋，但重複刷取不能無限增強能力。
- 戰鬥開始時凍結能力快照、消耗精力並記錄戰鬥 ID；中途關閉後能恢復或直接結算同一場，不得藉重開重擲結果。
- 好友對戰放在後續獨立階段，以好友碼挑戰對方保存的怪獸快照，屬非同步對戰，不要求兩人同時在線。
- 好友對戰最小後端需包含玩家身分、好友碼解析、怪獸快照、版本、戰鬥請求、結果與戰報。伺服器驗證能力與請求，使用固定種子執行版本化規則，並以戰鬥 ID 防止重複結算。
- 正式競爭功能須有可信的能力成長紀錄；不可直接相信離線客戶端上傳的任意能力、勝負或獎勵。若首版只接受本機快照，明確定位為無排行的好友娛樂對戰。
- 本機修改與步數來源不能被描述為完全防作弊；MVP 先不做排名獎勵、交易或賭注。先讓養成與對戰好玩。

**8. 畫面、美術與聲音**

- 手機直式、單手操作；主畫面上方顯示名字與狀態，中間是怪獸房間，下方為七項功能與孵化進度入口。
- 使用 2D 像素風：角色以 32×32 或 64×64 為起點、有限調色盤、清晰輪廓、nearest filtering。像素舞台以整數倍放大；文字與可點擊 UI 另行處理以維持可讀性。
- 外框可參考掌上電子機的塑膠質感，搭配 LCD 風格內框；也要有辨識清楚的彩色像素模式。
- 觸控目標以至少約 44pt／48dp 的實際顯示尺寸為目標，依裝置縮放換算，不把設計稿像素直接當成實機大小。支援安全區與常見長螢幕比例。
- 至少有待機、走動、吃東西、開心、訓練、攻擊、受擊、睡眠、生病、受傷、勝利、失敗與進化動畫；MVP 可先用少量影格，但每個狀態需可辨識。
- 音效短、清楚、有節奏；餵食、清潔、訓練命中、升級與破殼具有不同聲音辨識。BGM 低干擾，提供音量與震動開關。
- 沒有素材時先使用可替換的像素佔位素材，提出 sprite sheet 尺寸、影格數、命名與資源清單，不讓缺少美術阻塞遊戲邏輯。

**9. Godot 架構與存檔**

- 使用 Godot 4.x 與具型別標註的 GDScript；選定版本後保持一致。原生 Android／iOS 輸出為目標，Web 預覽只能驗證部分玩法，不能代表原生步數已完成。
- 以 Resource 或明確 schema 的資料檔定義怪獸、食物、訓練、進化與戰鬥參數。
- 拆分 PetModel、CareService、TimeService、StepService、HatchService、EvolutionService、BattleService、SaveService；依實際需要使用節點與 autoload，不把全部類別都做成全域單例。
- UI 使用 signals 更新顯示；時間結算、進化與戰鬥規則可以脫離畫面測試。
- 存檔包含 schema_version、怪獸狀態、收藏個體、蛋 ID、孵化起點、已入帳步數、來源與結算紀錄、最後照顧結算時間、成長紀錄、進化結果、未完成戰鬥與設定。
- 重要操作完成及 App 進入背景時保存；採暫存寫入後替換與備份，讓寵物變化和對應結算紀錄一起落盤，避免中斷後重複獎勵。
- 對原生串接、步數重複入帳、離線結算、進化重複觸發與存檔恢復做必要驗證。不要只證明按鈕有反應。

**10. 開發順序、驗收與交付**

階段 A：可玩核心原型。

- 完成直式主畫面、七項功能、MockStepProvider 孵化、一條含三種成熟分支的成長流程、NPC 戰鬥與本機存檔。
- 在開發模式 10 分鐘內可走完「蛋 → 孵化 → 餵食 → 訓練 → 戰鬥 → 進化」；正式版不使用這個加速時間。
- 重開後狀態正確，離線照顧規則可驗證；只能宣稱模擬步數核心原型完成。

階段 B：手機步行 MVP。

- 分別完成 Android 與 iOS 原生步數串接、權限流程及實機驗證；可依現有設備先完成其中一個平台。
- 驗證前景、背景、鎖屏、程式被終止後重開、跨日、手機重啟、撤銷授權、無來源、延遲同步與重複回傳。
- 對實際支援的來源與裝置，關閉遊戲走路後再次開啟能回補可取得的期間步數；重複同步不加倍。無法補讀的情境明確顯示並提供替代孵化。
- 未完成某平台實機測試時，列為未驗證，不能把兩平台全部標記完成。

階段 C：好友對戰與內容擴充。

- 完成好友碼、非同步對戰後端與戰報；使用兩個不同玩家身分驗證完整流程、斷線重試與防重複結算。
- 擴充怪獸圖鑑、外觀、蛋種與照顧事件。即時 PVP 與排行榜留待核心體驗驗證後再評估。

請依序交付：

1. 一頁式遊戲設計摘要、採用的預設與各階段範圍。
2. 主畫面配置、玩家流程與養成狀態轉移。
3. 數值表、進化條件表、戰鬥規則與資料結構。
4. Godot 專案目錄、場景結構與資源清單。
5. 當前階段完整可執行的程式與最小素材；每個程式區塊標明檔案位置。
6. 執行與手機匯出步驟、必要 SDK／簽署設定、原生外掛編譯說明。
7. 驗收結果：已實作、已測試、尚未驗證、待處理項目分開列出。

若有檔案系統與執行工具，直接建立專案並完成階段 A；缺少 Godot、SDK 或實機時，交付可檢查的原始碼與驗證方法，明確描述限制。先完成當前可驗證階段，再接續下一階段，不要一次鋪開所有模組而沒有可玩的版本。設計細節不足時先採合理預設並列出，只有會實質改變平台或核心範圍的問題才向我確認。
