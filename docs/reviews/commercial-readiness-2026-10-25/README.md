# godot-kit 與三款遊戲：商業完成度及程式碼評論

日期：2026-10-25。評估基準：工作樹現況，HEAD `01964ab`，包含本日尚未提交的 kit 新模組。這是改善決策文件，沒有實作修正，也沒有 commit。

## 結論

**三款都有值得保留的核心，但目前都不宜按完整商業遊戲驗收。主要差距不是功能數量，而是玩家是否看得懂、選擇是否有意義、進度是否可信，以及一次完整體驗是否足夠好。**

以小型獨立商業遊戲的要求評估：可以短、可以風格化、可以只服務一種玩家；但要完整履行它對這種玩家的承諾。沒有因為不是大型團隊就要求上百關、全語音、連線或雲端存檔。

| 對象 | 最有價值的部分 | 商業完成度判斷 | 最該先改善 |
|---|---|---|---|
| godot-kit | 儲存、可測試性、可編輯 scene、批量 sprite 呈現等低層能力 | 有用的內部工具箱；尚不是具版本契約的正式 SDK | 測試閘門可信度、模組狀態／同步契約、存檔故障邊界 |
| debt-commission | 「找證據→抓破綻→吐槽演出」與可辨認的和紙閱讀外觀 | 三者中閱讀／創作工具最完整；完整一集的品質仍待真人驗證 | 喜劇節奏、試錯成本、第一章收斂、進度保存一致性 |
| skybound-blades | 三人分工＋出營／補給／撤退／傳承的風險循環 | 最接近可擴充 RPG 閉環；有已重現的進度與技能缺陷 | 存讀檔和連招正確性、手機文字、永久死亡的公平感 |
| hero-horde-idle | 一指調度百人、六區閃避與敗因戰報 | 明確的戰鬥假說原型；尚未形成放置養成產品 | 先完成小型「打王→理解→養成→再挑戰」，同時修統計與時間模型 |

本輪沒有玩家樣本、商店轉換、留存、實機 profiler，**不給假精準的 8.3 分，也不預測銷量**。這是以玩家、開發者、評論者三個視角做的具證據評估，不冒充數十小時真人試玩。

## 什麼是事實，什麼是判斷

- **重現確認**：本輪執行小型 probe 或截圖確認；附輸入、輸出或圖片。
- **程式確認**：讀到實際控制流程／資料結構，可定位到檔案與行號；未必做過斷電或裝置故障注入。
- **設計判斷**：依現有玩法推導的優缺點；需要真人測試決定是否採用。
- **待測**：Android/iOS、正式 Web export、長時間負載、音訊聽感、付費意願及素材商業使用文件的完整性。本輪沒有把它們算通過。

審查抽讀核心實作及相依處，不是全倉逐行審計；技能採用 Studio `code-review`，各專案 config bootstrap 已執行，Godot 為 4.7。未做完整 ADR traceability，未宣稱遵循所有 ADR。商業評論也不等於發行簽核。

## 三款各自要建立的回饋循環

```text
討債委託  看懂線索 → 抓到破綻 → 選擇吐槽 → 獲得笑點／新資訊
                           ↑                 │
                           └── 有幫助的失敗反應 ┘

浮空劍域  出營準備 → 戰鬥與承擔風險 → 撤回結算 → 調裝備／連招
                           │                        │
                           └── 死亡／傳承           └→ 再出營

全員推王  調整隊伍 → 六區推王 → 看懂敗因 → 投資成長 → 再挑戰
```

目前三款的共通弱點是「下一次該做什麼，為何值得做」還未完全接上。更多技能、更多章節或更多英雄，會放大這個缺口。

## 建議工作順序

1. 先修 P1 的資料正確性與測試閘門，保住可玩成果。
2. 三款各選一個明確可交付單位：一個完整短篇、一趟含 Boss 的遠征、一個含養成回訪的推王循環。
3. 各找少量目標玩家做無提示試玩，觀察首次停住的位置、一次失敗後能否解釋原因、是否主動重試。建議先以 5 人做診斷，這不是統計顯著性或商業成功門檻。
4. 依觀察決定內容擴充，而非三款同時增加系統。

這些是後續改善提案；本次交付只新增評估文件及其證據。
