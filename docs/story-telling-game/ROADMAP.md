# 直式說故事遊戲 Roadmap

更新：2026-09-21。狀態：故事產出驗證進行中，Godot 尚未開始實作。

目標：用 Godot 完成一款固定故事的直式遊戲，先提供瀏覽器試玩。玩家透過閱讀、角色演出、選擇與少量地圖探索推進故事；完成這款遊戲後，再整理值得重用的功能。

依據為本次使用者確認，以及 [conversation3](base/conversation3.md) 的最後方向；[conversation1](base/conversation1.md)、[conversation2](base/conversation2.md) 補充介面、外觀與存檔需求。conversation3 第 796 行起確立故事優先，第 1237 行起列出開發順序，第 1385 行起提出 StoryRunner v0.1。

故事產出結合 [gintama-like](../gintama-like/story-prompt.md) 的共同編劇、喜劇與導演方法，以及 [interactive-fiction](../interactive-fiction/ROADMAP.md) 的互動敘事與試讀方法。使用者已選定新八視角的新故事《請幫我向你老闆討債》，先驗證人物對話與選擇回應；具體流程見 [STORY_WORKFLOW.md](STORY_WORKFLOW.md)，目前產物為 [第一場 draft-v0.1](stories/002-debt-commission-draft-v0.1.md)。

| 完整篇幅 | 依文本與故事規模決定，以場景／章節逐步製作，暫不預設總遊玩時數 |
| 核心循環 | 故事 → 對話與演出 → 選擇 → 狀態改變 → 後續故事，段落間穿插探索 |

本 roadmap 沿用 conversation3 的四方向移動方案。地圖尺寸、格子像素、衣服數量與存檔槽數，屬於需要配合這個故事收斂的製作規格；文件內的範例數字不當成固定交付數量。

| **M4：故事中的地圖探索** | 可以在一個小場景走動、找人、調查並接回劇情 | 格子座標、尋路、四方向移動、占位；點 NPC 自動靠近；互動與一次性觸發；探索／演出共用移動能力 | 插入一段有敘事目的的探索，例如調查線索後返回對話 | 劇情 → 探索 → 互動 → 劇情能連續完成；無路可走有回饋，一次性事件不重播 |
| **M5：角色外觀與直式視覺** | 角色在地圖與對話中具有一致外觀，手機閱讀舒服 | 玩家／NPC 共用外觀資料，地圖與立繪兩套 Renderer；紙娃娃對位、四方向動畫、UI 適配 | 製作該段故事需要的角色、表情、地圖與音樂；先完成少量成套素材 | 至少一個角色更換外觀時，SD 與立繪同步；所有出場角色可正確顯示，長台詞與選項不被遮擋 |
| **M6：完整試玩章節** | 一段有開場、衝突、選擇、結果的完整體驗 | 整合載入、劇情、演出、探索、存檔與設定；修正試玩阻塞 | 建議做 5–10 分鐘的完整短篇或章節切片，實際長度依劇本確認 | 新玩家不靠口頭說明即可玩完、理解事件與選擇後果；可分享瀏覽器試玩版本 |
| **M7：完成固定故事遊戲** | 從開始到結局可完整遊玩的作品 | 依實際缺口補功能、全流程回歸、資產與載入優化、版本化發佈 | 依場景逐段完成剩餘劇本、演出、美術與聲音；校對分支及結局 | 所有必要路徑可達結局，存讀檔一致，目標瀏覽器通過驗收，交付正式可玩網址與版本紀錄 |

主線順序：**S0 故事驗證 → M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7**。S0 先交付可試讀的內容與觀察，再把有效片段帶入 Godot。M2 確認演出需求後，美術規格與少量素材試製可以和 M3／M4 並行；M5 的雙 Renderer 與動畫驗收需要前面已穩定的角色介面。

S0 以文本／人工選擇驗證故事；M1 是技術原型，M6 是代表最終品質的試玩切片，M7 才是完整遊戲。M0 起每階段都保留可執行的瀏覽器版本。先依成果驗收，待 M1／M2 量到一段劇情的實際製作成本，再按完整篇幅、人力與素材成本估算日曆工期。

配合本次瀏覽器先行的決定，最小續讀驗證安排在 M3，以便在擴大故事內容前確認選擇與閱讀進度能保留；地圖位置、外觀等完整存讀檔整合在 M4–M6 完成。

## 第一個實作目標：一分鐘故事

StoryRunner v0.1 依 conversation3 的六個指令起步：

| 指令 | 最小責任 |
| --- | --- |
| `say` | 指定說話者與台詞，等待閱讀推進 |
| `choice` | 顯示選項，依選擇跳到指定節點 |
| `move` | 將指定角色移到舞台標記，完成後繼續 |
| `face` | 讓角色朝指定方向或對象轉身 |
| `wait` | 控制停頓時間 |
| `set_flag` | 寫入劇情狀態 |

劇本另有穩定的節點 ID、入口、跳轉與結束規則。M1 的選項可以直接走不同節點並設定旗標；M2 再加入依既有狀態判斷的 `condition`，讓稍後的對話回應先前選擇。

首段驗收劇本的形狀：舞台上已有角色 A 與主角 → 對話 → A 走到另一個站位 → 主角轉身 → 玩家選擇 → 不同反應與旗標 → 段落結束。實際台詞取自 S0 選定的故事片段；M1／M2 可以使用佔位角色與表情素材。

M1 的移動在空白舞台上使用命名站位即可。M4 再接上格子、障礙與尋路；`StoryRunner` 與玩家輸入共用底層角色移動能力，劇本只表達「誰到哪裡」。

## 直式畫面的驗收

- **閱讀狀態：** 下方固定閱讀區，上方保留角色與場景；立繪站位先支援左／中／右。說話者醒目，文字大小與速度可調整。
- **選擇狀態：** 選項放在容易觸及的下半部；長選項可換行。選項很多時，選項區可捲動且不推進台詞。
- **探索狀態：** 地圖為主，保留地點、下一步提示與選單入口；點地面有目的地回饋，點角色可自動靠近。
- **輸入規則：** 第一次點擊補完正在顯示的句子，再次點擊才前進；對話、選項、選單皆攔截地圖點擊。
- **控制權：** `PLAYER / STORY / MENU` 統一管理。選單關閉後返回原模式；演出失敗有可辨識錯誤及恢復方式，避免永久鎖住輸入。
- **尺寸驗證：** 覆蓋 9:16 與較長的手機比例、瀏海／安全區、瀏覽器工具列伸縮；桌機縮放視窗後仍維持直式構圖。以實際匯出頁的可用區域測試。

Godot 支援以基準尺寸搭配伸縮、錨點與容器處理不同畫面比例；原型先使用 720 × 1280 的 9:16 設計尺寸，正式素材規格在 M5 前確認。這是本次製作建議，設定依直式構圖測試調整。[Godot 多解析度文件](https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html#mobile-game-in-portrait-mode)

## 故事資料、演出與存檔的邊界

- **劇本來源：** 只選一種易讀、可版本控制的格式作為真實來源。先使用 JSON 作為執行資料的候選；M0 用第一段劇本確認作者編寫方式與匯入流程。作者可先寫普通對話與演出註記，再轉為結構資料。
- **執行器：** 每個指令都有完成、失敗與取消的結果。第一版以順序執行為主，先滿足這個故事實際出現的演出。
- **資料檢查：** 缺角色、缺站位、跳到不存在節點、未知指令與錯誤變數型別，應在預覽前指出劇本及節點位置。
- **角色資料：** 角色 ID、外觀 ID、地圖角色與對話立繪分開；外觀資料共用，圖片資源與動畫由各自 Renderer 處理。
- **存檔設計：** M0／M1 就定義資料版本與穩定 ID，M3 實作最小續讀，M4／M5 再加入地圖與外觀狀態。
- **檢查點：** 先在明確的閱讀／段落邊界提交完整狀態。存檔包含故事／節點位置、變數、已完成事件及重建舞台所需資料；讀檔從最近一次成功檢查點恢復。台詞可以重讀，選擇效果不能重複套用。中途關閉時，最多回到上一檢查點。

實作位置在 M0 確認：本 repo 是 Godogen 原始碼，遊戲需有獨立的 Godot 專案根目錄與匯出設定。可沿用 repo 的 `prototypes/` 慣例開發首個原型；既有 runtime manifest、publish 腳本與其他遊戲不屬於本 roadmap 的實作範圍。

## Godot 瀏覽器交付

實作技術建議採 Godot 2D、GDScript、Compatibility Renderer 與單執行緒 Web 匯出，於 M0 驗證並鎖定相容的引擎和匯出範本版本。目前 Godot 4 Web 匯出使用 Compatibility／WebGL 2.0，單執行緒也是官方預設方案。[Godot Web 匯出文件](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

- M0 先測試中文、點擊、音效啟動與資料持久化；之後每個里程碑都交付 Web 匯出版本。
- 以「點擊開始」作為音效啟動入口；測試切到其他分頁再回來後，演出與音樂的狀態。
- M3 驗證同一瀏覽器、同一網址重新開啟後可以續讀；不能只以編輯器內存檔成功當作通過。
- 瀏覽器存檔受網站儲存政策影響，受限模式可能無法持久保存。實作時若發現無法儲存，要讓玩家理解實際狀態。[Godot Web 持久化與音效限制](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html#limitations)
- 試玩驗收至少安排桌機瀏覽器與手機實機；預計覆蓋 Android Chrome、iOS Safari。未測到的平台如實標示，M0 確認可取得的裝置。
- M6／M7 驗證首次載入、觸控、中文字型、聲音、背景切換與重新開啟。記錄匯出包大小及目標裝置上的載入時間，依實測設定預算。
- 開發時使用本機 HTTP 伺服器，對外試玩版本使用 HTTPS；部署位置在交付前確認。

## 試玩切片的建議範圍

以下是 M6 的範圍提案，用來控制第一次整合成本。一分鐘原型與 5–10 分鐘試玩切片是驗證單位；完整遊戲的篇幅依文本與故事規模決定。

| 內容 | 建議起點 |
| --- | --- |
| 遊玩長度 | 5–10 分鐘，包含起承轉合 |
| 場景 | 一個小場景，具有 2–3 個劇情站位／互動點 |
| 角色 | 一位主角、兩位 NPC；依故事需要調整 |
| 分支 | 2–3 次選擇，其中至少一次在稍後明確產生不同反應；可回到共同主線 |
| 探索 | 一段短探索，連接兩段劇情，提供線索或改變玩家理解 |
| 外觀 | 每位出場角色有一套完整外觀；挑至少一位角色驗證兩套外觀同步切換 |
| 表情 | 先備齊片段用到的表情，預計 3–4 種起步 |
| 續讀 | 一個自動存檔／繼續入口、對話紀錄、字速與音量設定 |
| 結尾 | 一個完整段落結尾，能看出至少一個選擇的後果 |

素材試製前先列出角色、立繪、方向／動畫與場景資產清單。涉及 AI 圖像時，再由使用者選擇直接生成，或提供可交給 opt image 的提示詞；本次 roadmap 不包含圖像生成。

## 固定故事的內容製作

先依 [故事產出流程](STORY_WORKFLOW.md) 從新種子形成角色與節拍，再拆成「場景目的 → 衝突 → 玩家行動／選擇 → 後果 → 下個場景」。每個場景同時標出需要的角色、站位、表情、音樂、變數與前置條件。

S0 先精寫並試讀一個完整段落，由作者回饋調整方向；再從中挑選 M1 的一分鐘演出測試，並擴成 M6 的試玩切片。其他章節先保留事件與分支大綱。M6 驗證閱讀與演出節奏後，再逐場景完成剩餘內容，每一場都以可在遊戲中播放為完成條件。

M7 以章節滾動規劃。每章先統計必要場景、獨有角色／素材與可達分支，完成後量測實際閱讀、選擇、探索和演出時間，再更新後續工作量與整體篇幅估計。驗收以故事完整與內容可玩為準。

優先採用分支後回到共同主線、以旗標保留差異的結構。只有故事需要時才拉出長路線或不同結局。主角是否可自訂姓名、外觀與人設，需配合固定故事另訂範圍；紙娃娃能力本身不代表必須有完整捏角流程。

試玩回饋聚焦：玩家是否知道誰在說話、發生了什麼、選擇造成什麼結果，以及是否想繼續看。依此修正文本與演出，再擴大內容。

## 後續功能與待確認事項

MVP 先聚焦已確認的敘事功能。背包、任務介面、好感度頁面、時間系統與小地圖，依實際劇本需要加入；故事條件可先由旗標與變數承擔。戰鬥、商城、雲端存檔、配音、大量服裝與完整圖形化劇情編輯器屬於後續評估項目。

完整遊戲穩定後，再根據真實重複工作抽出故事播放器、演出元件與素材規格。是否適合支援第二款故事，屆時以實際內容驗證。

目前待確認：

1. 依 [第一場試稿](stories/002-debt-commission-draft-v0.1.md) 收集角色語氣、喜劇節奏與選擇回應的作者回饋，完成一次改稿與試讀。
