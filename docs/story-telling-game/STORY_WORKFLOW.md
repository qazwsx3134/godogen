# 故事產出與驗證流程

更新：2026-09-23。用途：驗證故事能否透過共同編劇產出、改稿與試讀，並交付 Godot 演出。搭配 [遊戲 Roadmap](ROADMAP.md) 的第一章劇本製作。

本輪已確認：使用銀魂角色，從新的故事種子開始；使用者選定 B《請幫我向你老闆討債》，新八視角，先驗證人物對話與選擇回應。候選歷程見 [001-story-seeds.md](stories/001-story-seeds.md)，產物見 [第一場 draft-v0.1](stories/002-debt-commission-draft-v0.1.md)。作者已確認文章可用並要求先完成 Godot 演出；本輪直接把完整第一場帶入 [Godot 專案](../../prototypes/debt-commission/README.md)，從可玩版本收集閱讀節奏和分支回應的回饋。真人試玩結果仍待收集。

## 來源如何配合

| 來源 | 採用內容 | 在本案的用途 |
| --- | --- | --- |
| [gintama-like/story-prompt.md](../gintama-like/story-prompt.md) | 主角 → 展開方向 → 失控點 → 角色功能 → 節拍 → 關鍵對話方案；導演模式 | 和作者逐步形成故事，並提早檢查演出需求 |
| [gintama-like/chat-1.md](../gintama-like/chat-1.md) | 小事放大、荒謬升級、角色反差、認真後回到日常 | 建立喜劇的因果與節奏 |
| [gintama-like/chat-2.md](../gintama-like/chat-2.md) | 角色關係、反覆笑點、已知資訊與後續影響 | 讓先前的選擇或觀察在稍後被角色記住 |
| [gintama-like/chat-3.md](../gintama-like/chat-3.md) | 先驗證文字與吐槽；《消失的草莓牛奶》故事種子 | 提供可比較的既有內容，先試讀局部段落 |
| [interactive-fiction/ROADMAP.md](../interactive-fiction/ROADMAP.md) | 閱讀、調查、選擇、線索、後果、收尾；作者改稿與真人試玩 | 把故事改成能由玩家參與的內容，分開記錄製作與體驗驗證 |

本案的呈現契約是 **Godot、瀏覽器先行、直式、Top-down 地圖加對話 Overlay**。敘事視角表示玩家跟隨誰的知識、目標與選擇；例如跟隨銀時，仍能使用俯視地圖與立繪。舊互動小說案的 2D 主觀鏡頭、Vite／TypeScript 製作路線，保留為該案的脈絡。

完整故事篇幅依文本與情節決定。短片 prompt 的預設片長、舊 roadmap 的時數與系統數量，作為參考尺度；本案依每個驗證片段實際需要安排。時間輪迴、QTE、戰鬥與小遊戲若出現在構想裡，先記成待驗證需求。

## S0 的產物與順序

| 步驟 | 工作 | 具體產物 | 通過條件 |
| --- | --- | --- | --- |
| S0.1 故事起點 | 選既有故事或新種子，確認主角、目標、角色關係與創作限制 | 一頁故事簡介，列出已決定與待決定事項 | 作者能說明想看哪件事如何發展 |
| S0.2 共同編劇 | 提出不同展開與失控方案，依作者選擇形成節拍 | 場景節拍表、角色功能表、關鍵對話候選 | 事件有因果；角色分工清楚；收尾回扣目標 |
| S0.3 互動試稿 | 寫一個可試讀段落，加上玩家選項、即時反應與稍後呼應 | 玩家可讀文本、分支去向、少量狀態與演出註記 | 每個選項可讀到結果，分支合流後仍保留先前行動的影響 |
| S0.4 改稿驗證 | 作者修改一段台詞、一個選項反應；逐路徑朗讀檢查 | 有版本號的試稿、變更摘要、作者檢查紀錄 | 改稿可定位；人物知識、線索與後果一致 |
| S0.5 真人試讀 | 先找 3 位未看過草稿的人，以訊息或分段文本進行；正式短篇再擴到 5 人 | 試讀紀錄、問題清單、修訂版本 | 依下方內容標準評估；真人結果與作者自查分別記錄 |
| S0.6 交付遊戲改編 | 選定通過試讀的片段，列出演出與資料需求 | 劇情節點、分支／狀態表、站位與資產需求 | 可清楚對應到 M0／M1 的故事片段，功能缺口有具體場景依據 |

第一輪先驗證一個段落的產出與修訂。接著再把同一故事推到有完整收尾的短篇；依內容決定長度。

「作者選項」是共同編劇時用來決定走向、喜劇方式與台詞版本的候選；「玩家選項」是定稿後仍留在作品內、會改變回應或狀態的分支。作者挑掉的方案不會自動變成遊戲分支。

## 可直接使用的遊戲編劇 Prompt

以下可作為故事產出工作階段的起始指令。已有決策與文本可以直接填在最後的輸入區。

```text
你是與作者共同工作的互動敘事編劇與 2D 遊戲演出設計師。

作品目標
- 先完成一款固定故事的遊戲。使用 Godot，瀏覽器先行，直式顯示。
- 地圖為 Top-down，對話與角色立繪覆蓋在地圖上。
- 本階段交付可試讀、可改稿的故事。完整篇幅由文本與故事規模決定。
- AI 協助製作階段的編劇；玩家遊玩時依定稿內容執行。

創作原則
- 從角色真正想完成的小目標開始，讓行動引發下一個麻煩。
- 使用日常、荒謬升級、角色反差、吐槽與回扣；認真段落依角色需要安排。
- 為每位角色定義欲望、說話習慣與戲劇功能，保持人物可辨識。
- 吐槽要指出具體矛盾、改變關係或推進事件。
- 可用沉默、動作、表情與音效形成笑點；關鍵線索仍要能從文字理解。
- 若作者選擇跨類型惡搞，讓角色行動與敘事規則的衝突成為笑點來源。
- 保持既有角色、世界與已確認事件的一致性；新增設定標為提案。

互動方式
1. 先讀「本輪輸入」，整理已確認決策。已提供的主角、種子與限制直接沿用。
2. 對會改變故事方向的缺口提出簡短問題；其餘細節提出可修改的假設。
3. 故事方向未定時，提供 3 個戲劇核心不同的作者選項。每個包含：
   一句話展開、主角動機、荒謬升級的因果、可能的情緒落點、製作成本。
4. 作者選定方向後，提供失控點、角色功能與節拍表；視回覆把必要決策合併，
   不機械地重問已確定事項。主要方向由作者選定後，再展開完整短篇。
5. 先對一個重要場景提供 2–3 種對話處理，形成可以比較的短試稿。
6. 採用的版本轉成互動文本。每個玩家選項都有可理解的意圖、角色反應、
   狀態變化與後續去向；至少一個選擇在稍後產生可辨識的呼應。
7. 作者要求你直接決定時，可以完成該範圍的草稿，並列出採用的假設。

互動敘事規則
- 先寫清楚玩家是誰、目前要做什麼、有哪些已知資訊。
- 把作者知道的真相、角色知道的事、玩家已看到的線索分開。
- 若有推理，先提供可察覺的證據，再要求判斷；答錯可得到反應或提示並繼續。
- 初次驗證以自行閱讀、無限時選擇為基準。若要測限時吐槽，另列對照假說。
- 分支可回到共同主線；合流後仍要讀取已記錄的影響。
- 有正確答案的選擇需有劇內依據；人物態度／喜劇回應可有不同後果。
- 同一版故事使用穩定的場景與節點 ID；狀態列出初始值、寫入點與讀取點。

遊戲導演模式
- 每場列出角色、場景、道具、表情、站位、移動、鏡頭、BGM／SE 與文字節奏。
- 將需求分成「理解故事必要」「可用低成本方式替代」「加分演出」。
- 高成本場面提供可讀的替代，例如角色反應、黑畫面加聲音、剪影、靜態姿勢。
- Roadmap 規劃的第一批能力是 say / choice / move / face / wait / set_flag；
  camera / expression / bgm / sound / fade / condition 屬於後續演出能力。
- 劇本可以寫出需要的效果，但要標示能力缺口；先用人工試讀驗證效果。

每輪輸出
- 已確認決策、目前待作者選擇的事項。
- 本輪候選或試稿，附版本與修改範圍。
- 玩家看得到的文本，和作者用的分支／狀態／演出備註分開。
- 一項具體的驗證問題與觀察方式。
- 此輪完成後下一個最小工作單位。

完整片段交付格式
作品／片段 ID、版本、敘事主角、目標、角色功能。
Beat 表：節拍 → 因果 → 玩家行動 → 即時回應 → 後續呼應。
節點稿：ID、玩家文本、說話者、玩家選項、下一節點、演出註記。
狀態表：名稱、初始值、何處寫入、何處讀取、可見後果。
路徑表：每條路徑的入口、選擇、合流／結尾、預期結果。
資產／能力需求、作者自查結果、真人試讀待辦。

本輪輸入
故事種子或既有文本：
主角／敘事視角：
已確認的事件與角色：
想保留的氣質或台詞：
本輪要改的一段：
需要作者選擇／可由你決定的範圍：
```

## 故事驗證方式

先測閱讀與選擇本身。試讀者只看到目前段落及可選行動；主持人依選項給下一段，保留作者狀態表。演出可用短括號註記。評估結果若依賴讀者想像，記錄後在 M1／M2 的實際演出再次驗證。

| 驗證面向 | 觀察與問題 | 第一輪通過目標 |
| --- | --- | --- |
| 故事理解 | 讀完後說明主角、當前目標與事情變糟的原因 | 3 人都能走到片段結尾，至少 2 人說清楚目標與因果 |
| 角色與喜劇 | 記錄停頓、困惑、自發反應；請讀者指出有效或無效的台詞 | 至少 2 人指出具體角色反差或有效笑點；不以「有沒有大笑」作唯一標準 |
| 互動後果 | 問「你剛才做了什麼，哪個回應因而發生？」 | 至少 2 人能連結一次選擇與稍後的回應 |
| 持續閱讀 | 在段落收束處詢問是否想讀下一段、對什麼感興趣 | 至少 2 人想繼續且說得出人物或事件理由 |
| 改稿可行性 | 作者改一段台詞與一個選項結果，再各走一次相關路徑 | 修改可定位，所有受影響路徑仍可到結尾；記錄所需時間與協助 |

這些數字是小樣本的工作目標。作者自查可發現斷路與資訊矛盾；真人試讀才能提供讀者理解、喜劇效果與持續閱讀意願的證據。沒有試讀者資料時，狀態填「待試讀」。

試讀紀錄最少包含：版本、讀者代號、路徑、實際閱讀時間、困惑的句子、選擇理由、注意到的後果、想不想繼續、主持人是否給提示。改稿列出改動前後的節點，保留原版以便比較。

## 既有內容的比較基線

現有 [missingStrawberryMilk.ts](../../prototypes/missing-strawberry-milk/src/data/scenes/missingStrawberryMilk.ts) 提供內容結構的比較基線：牛奶不見 → 先問新八／神樂／房東 → 黑影登場 → 吐槽 → 兩種收尾。本輪的故事樣本使用新種子。

既有詢問選項會寫入 `asked:*`，故事資料目前沒有依這些旗標安排後續呼應。新故事會把「一次選擇寫進人物記憶，稍後有可見回應」列為首輪驗證項目。新增樣稿獨立保存於本目錄的 `stories/`，原型與舊故事檔維持比較基線。

原型的兩秒吐槽、三個回答與成功／失敗收尾可作功能參考；故事產出試讀先採無限時選擇，計時效果在有文本基線後另測。原型已有的功能測試紀錄不代表本次內容或 Godot 版本已通過驗證。

本輪依作者核准的互動試稿推導 M0／M1 的內容與演出需求，執行資料使用 [debt_story.json](../../prototypes/debt-commission/data/debt_story.json)。Markdown 節點稿保留為作者文本；Godot 的 StoryRunner 讀取 JSON。真人試玩與後續改稿沿用上述觀察方式。
