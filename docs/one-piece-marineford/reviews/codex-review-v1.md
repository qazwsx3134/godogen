## 2. PokeBonk 畫面與渲染層

**參考搬移：整體方向同意，但「同」不能理解為數值與成本直接等價。** D:29–43 與 L:59–76、87–104 的背後低鏡頭、下方角色構圖、toon＋描邊、旋轉 XP、硬陰影與紙卡方向一致；真 3D 與較細緻主角被共同調色統一是對的。漏掉最影響畫面接近程度的 **天空漸層、方向光與地面／天空環境光、接地陰影、霧的遠近分層與遠景剪影**（A:25、49，L:82–90）；只做低模＋三階 toon＋後製，冰海仍可能像平板灰盒。需在廣場 spike 用代表性冷藍色材質、天光、投影、地平線軍艦／處刑台剪影驗構圖，暖黃草原色票不必硬搬。D:34 深度描邊和 D:35 的主角可見是兩個不同系統：A:17 的 Always visible 是另畫玩家 silhouette 再做兩層螢幕輪廓，普通 inverted hull 不會自然穿海兵與透明特效；D:259 必須定清楚採角色專用 viewport／遮罩合成或明確 depth-test 策略，以及 UI／閃屏／後製誰先誰後。D:37 把五滑桿寫成含 FOV punch，與 L:61 的 Hit-stop／Shake／Flash／Impact Distortion／Effect Strength 不同；FOV punch 可作 Effect Strength 的子項或獨立第六項，但別稱原版五項完全相同。D:36 複製 bloom 0.55／0.3／2.4 遺漏 A:39 的 Always visible 開啟時 strength 實為 0.4×設定，且 Three.js UnrealBloom 的 radius／threshold 不等於 Godot Glow 同名值，須靠對照圖調參。D:40–42 只列版位和配色，還應明確保留卡片的「前→後」、類別圖示／稀有度帶及字級層次；新招式 3D 展示（L:35）可延後，但應標成不在切片範圍，不能用舊 madara HUD 當「畫面整套搬完」。

**Compatibility 可行性：深度描邊可行、Glow 已支援、CompositorEffect 不支援；多段串接仍是實作風險。** [Godot 4.7 renderer 功能表](https://docs.godotengine.org/en/4.7/tutorials/rendering/renderers.html#environment-and-post-processing) 明列 Compatibility 的 fullscreen quad、screen／depth texture、Glow 支援，CompositorEffects 不支援；Normal/Roughness buffer 不支援，內建 DOF 也不支援。因此 D:59 的 CompositorEffect 判斷正確，但「深度紋理與 Glow 支援程度待實測」應收斂為「已有官方支援，畫面品質、Web 驅動與效能待實測」。[4.7 進階後製文件](https://docs.godotengine.org/en/4.7/tutorials/shaders/advanced_postprocessing.html) 給出 Compatibility 的 OpenGL NDC 重建分支；不直接套 Forward+ 深度公式／reverse-Z 假設，深度只能從所在 viewport 存取。採 view-space 線性深度做輪廓與焦距，測遠近地板交界／薄柵欄，避免全屏遠景變黑邊。移軸須自訂深度感知 blur，不能以內建 DOF 已可用作前提。[4.7 Environment 文件](https://docs.godotengine.org/en/4.7/tutorials/3d/environment_and_post_processing.html#glow) 指出 GL Glow 是獨立簡化實作，部分屬性隱藏；安裝版 commit 的 [GLES3 renderer](https://github.com/godotengine/godot/blob/5b4e0cb0f/drivers/gles3/rasterizer_scene_gles3.cpp#L2667) 在 `_render_post_processing` 實際調用 `GLES3::Glow`／`process_glow`，並有 threshold／intensity 等參數。這足以確認引擎路徑存在，沒有在本輪跑 Web 視覺測試，故不保證特定瀏覽器效果或效能。官方 renderer 表另列 Compatibility 為 RGBA8 LDR；原參考 A:34 是半浮點 target，不能把 HDR 閾值 2.4 原樣當作 LDR 網頁可見 bloom 的保證。

**最關鍵的新技術缺口是 D:59 的「全畫面四邊形」沒有定義 pass 間資料流。** [官方 screen-reading 說明](https://docs.godotengine.org/en/4.7/tutorials/shaders/screen-reading_shaders.html#behind-the-scenes) 指出 3D screen texture 在 opaque 後、transparent 前拷貝，且不會因再畫一個讀屏材質就重新捕捉。故依序疊描邊 quad、移軸 quad、調色 quad，不代表後者讀得到前者輸出；透明拳影／蒸氣也不自然出現在讀屏來源內。建議 spike 交付實際的 render graph：同 viewport 的深度處理如何輸出顏色，後續用哪些 SubViewport／明確 render target 或 2D BackBufferCopy 取得上一步顏色，透明 VFX 在哪一步進來，內建 Glow 在哪一步執行，最後才合成主角保護輪廓與清晰 HUD。不要承諾任意 SubViewportTexture 就附帶可讀的深度，也不要把一般 3D quad 堆疊當成任意串接。可先用 GL 內建 Glow＋合併 outline/簡化 blur 的近似鏈做驗收，若與 A:27 的順序不同，列明差異交使用者看圖判斷；「只留描邊＋bloom」也要說明它確實避開哪段成本，不能當未定義管線的萬用退路。

**低鏡頭／觸控：風格成立，玩法風險比 v0 大，必須納入 spike。** D:29 的鏡頭朝目標與 D:116 C3／C7 後方追兵，會造成追兵及圈在鏡頭外；主角有輪廓不會讓前方被海兵擋住的雷射／毒圈自動可見。建議相機沿路線切線平滑朝前，提供邊緣追擊／危險方向標、艾斯鏡外標記與倒數聲，近處遮擋物可淡出或在關卡布置上避開；暫用正前方／側後方／正後方三個固定危險情境測能否在 1.5 秒預告內辨識並掩護／閃開。不要默認使用者右手可同時拖視角再按技能：三按鈕＋左搖桿已占兩指，固定／自動鏡頭最省操作，若加自由鏡頭須另定手勢優先權。M/scripts/main.gd:229–233 原本把 screen vector 直接當世界 XZ，改背後視角後必須依相機水平 forward/right 轉換；鏡頭旋轉時保持可預測的移動與火箭方向，否則向上可能在畫面側跑。16:9 是基準而非強制擠壓真機長寬比：HUD 與搖桿按可用安全區佈局，至少驗 16:9 與一個超寬橫向畫面、瀏海／瀏覽器工具列，右手三鍵不壓目標列／招式槽，menu 暫停時放掉手指 ownership。觸控 hit target 與字體給出可調規格、C6-A 真人雙指試玩再驗收；桌機 headless 過關不能代替手機輸入證據。

**第 0 步通過條件：部分可判定，尚不足以裁決「畫面像且可玩」。** D:308 的使用者並排判斷可作有效美術驗收，不要求機器判審美；但目前本機沒有 `.claude/tasks/pokebonk/shots/p00.png`（原文件引用的是另一台 `/Users/peter/...` 的路徑），需先取得可用參考或另選使用者可見的參考畫面，才有比較基線。不要因此去把第三方資產導入遊戲。D:306 只列灰盒與後製，卻想判讀 L 的整體質感；至少加代表光照／霧／配色、主角輪廓、一次透明拳影與一塊 HUD／橫幅。D:308 的 10 秒 p95≤20ms 可測，但需固定機器 CPU/GPU、Chromium 版本／WebGL renderer（硬體或 SwiftShader）、DPR／實際 render resolution、warm-up、品質 preset、是否關自動降解析度；否則 0.75 倍分辨率或自動關 bloom 也能拿「完整堆疊」通過。250 隻視錐內不等於 250 隻可見，低角度密集軍團本來會遮擋，應同時記 view-frustum count 與固定構圖截圖，不能靠把群體藏在畫面外／牆後過測。分別測靜態、沿路移動、一次群體受擊／霸王色；列 p95 與最慢幀，UI 與透明特效仍清楚。這些是視覺 spike 的驗收補全，不是要求先完成 C6 全套。失敗應先區分美術不合格、管線缺功能、或效能超標，再選擇調色／簡化 pass／換平台；「只做原生」會改交付平台，需由主導把具體證據交使用者決定。
