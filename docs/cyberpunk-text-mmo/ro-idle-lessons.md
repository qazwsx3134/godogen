# 借鏡 RO放置仙境：給本作的設計建議

日期：2026-11-04。依據 [ro-idle 研究](../research/ro-idle-2026-11-04.md)（公開資料、前端 bundle，以及 §11 的約 20 分鐘登入實測）。本檔是提案，不改寫 game-design、risk-systems、architecture 等已確認規格；採用哪一項由使用者決定。

## 1. 結論

ro-idle 最值得學的不是 RO 的內容，而是它怎麼讓「自動執行」被玩家信任：**規則看得懂、沒執行時說得出原因、死了知道為什麼、離開回來有報告、會出事的地方有保險絲**。這五件事剛好對應本作的 P0 缺口：自動段不能吞掉決策、失敗與死亡要能被理解。

本作與 ro-idle 的根本差異：

| | ro-idle | 本作 |
|---|---|---|
| 內容 | 可重複刷怪，226 張地圖 | 每角色一次性委託，有限案源 |
| 死亡 | 扣 1% 經驗，復活再掛 | 永久死亡 |
| 經濟 | 開放市場、交易、擺攤、轉蛋 | 有限經濟，首版無交易與抽卡 |
| 離線 | 離線照打，可能離線死亡 | 離線只跑安全段，危險節點等玩家 |

> 2026-11-04 更新：使用者改為雙層任務（[quest-layers.md](quest-layers.md)），可重複的街頭工作讓 ro-idle 的排隊掛機、停止條件、離開報告、週榜與全服目標更直接適用；#20 的 sink 設計改為「單人收支可參考」，市場與 PvP 仍不適用。

所以「刷」「市場」「PvP」相關設計大多不適用；「解釋」「報告」「保護」「共同貢獻」相關設計大多可以直接或改編後使用。

## 3. 最值得先做的四件事（對應 P0）

### 3.1 自動段要說得出「為什麼」

ro-idle 在每條規則下顯示不施放的原因，並在 FAQ 一再回答「技能怎麼只放一次」。玩家不信任自動化，多半是因為看不懂它為什麼沒做某件事。本作的對應位置：

```text
方案頁                      執行中的行動紀錄            結算頁
┌────────────────────┐     ┌────────────────────┐     ┌────────────────────┐
│ 強攻  評級 B       │     │ 03:12 繞開監控     │     │ 勉強完成           │
│  ✓ 火力 3/3        │     │   ← 準則：暴露上限 │     │ 因為：             │
│  ✗ 情報不足：守衛  │     │ 04:40 撤到 B 出口  │     │ ・缺守衛排班情報   │
│    排班未知 → -1級 │     │   ← 準則：傷勢中度 │     │ ・準則提前撤離     │
│ 入侵  不能選       │     │      即撤          │     │ 下次可以：…        │
│  ✗ 缺作業設備      │     └────────────────────┘     └────────────────────┘
└────────────────────┘
```

每一行理由都要指向玩家能改變的東西（能力、情報、裝備、準則）。這也是檢查 P0「方案是否只是能力門檻」的工具：如果理由永遠只有「能力不足」，方案就只有門檻差異。

### 3.2 死亡與險死要能回溯到選擇

ro-idle 的死亡紀錄會指出是玩家的哪個設定導致死亡。本作的永久死亡更需要這件事：玩家要能說出「我是因為哪個決定死的」，死亡才會被當成故事，而不是被當成系統不公。生涯結尾建議固定放：最後的節點與當時的選項、選擇時的狀態（傷勢、通緝、保單、壓力）、救援為什麼沒到、這段生涯的險死紀錄。

### 3.3 回來第一屏是報告，不是主畫面

ro-idle 補算完才放玩家進遊戲，先給離開期間報告。本作 S17 已有方向；建議報告固定三段，且等待中的危險節點永遠排第一，避免玩家先被聊天或排行吸走注意。

### 3.4 共同事件的獎勵不能被頭部玩家包走

ro-idle 的 MVP 原本傷害最高的隊伍全拿，改成兩份掉寶後，「有打就有機會」。本作城市事件同理：參與獎給所有有效貢獻者，排名只換展示。這同時回答 design-assessment §4：後進或輕度玩家也能感受到自己的貢獻。

## 4. 架構與營運上的提醒

1. **架構方向被驗證**：ro-idle 用 `commandId` 加 `expectedCommandRevision` 送指令、失敗重試，回應直接帶新狀態；推送用 SSE 帶 `after` 游標續傳，補不回時送 `gap` 要求重抓。這與 architecture §4 的 request_id／expected_version，以及 §7 聊天 last_sequence 的設計一致。
2. **舊分頁要被告知已被接手**：本作的 expected_version 已讓舊分頁的指令回 409，development-plan 也要求雙分頁只能發獎一次，所以兩個分頁不會各自提交不同結果。缺的是通知：ro-idle 用 `superseded` 事件告訴舊分頁「這個角色已在別處開啟」，舊分頁直接停用操作。本作的致命確認頁若只在送出後才拿到 409，玩家會在生死關頭看到一個技術錯誤；建議舊分頁在送出前就顯示「已在其他裝置開啟」並停用確認鈕。
3. **閒置斷線省成本**：畫面開著但 20 分鐘沒操作，ro-idle 就停掉即時推送、改為離線結算；有新版本時自動重新整理閒置分頁。這兩點可以直接降低 Cloudflare DO 的連線數與舊前端殘留。
4. **線上動作不能等離線方補算**：ro-idle 曾有交易、入隊、踢人、買攤位都卡在「補算離線進度」，最後改成不等待、直接生效，對方之後照常補算。本作的共同事件貢獻與週榜，若要求先推進其他玩家的狀態才能計算，會遇到同樣的問題；貢獻應在各自結算時獨立寫入。
5. **壞部署在本作是不可逆的**：ro-idle 有兩次改版當天撤回，其中一次讓部分角色的錢被花光；它可以退款、還原設定。本作的死亡是終態（risk-systems §1「不提供復活、讀舊檔」，architecture §5「DEAD 不得改回存活」），所以「因系統錯誤死亡」怎麼處理需要使用者事先決定。可選的做法：
   - (a) 窄例外：只有管理員確認是系統錯誤時，恢復到節點前。這會修改已確認的永久死亡規則。
   - (b) 不恢復：生涯紀錄標為「系統錯誤致死」，給下一個角色補償（不繼承戰力）。
   - (c) 只靠預防：獨立測試世界、功能開關、分批上線，不設事後處理。
   不論選哪個，開發計畫的獨立測試世界與功能開關都應列為上線前提。

   **2026-11-04 使用者決定**：系統錯誤致死改為 Trauma Team 免費搶救，角色存活但記錄在生涯裡（接近 (a)，用世界觀包裝），細節寫在 risk-systems §1。
6. **營運節奏**：ro-idle 更新紀錄可見的 20 天內有 239 筆更新，89 筆來自玩家回報。小團隊的現實是封測期間大量修正，所以公開更新紀錄、回報管道與「部署前未結算照舊規則」的說法，最好在第一次封測前就準備好。

## 5. 不建議學的

- **規則編輯器的完整深度**：ro-idle 的玩家本來就想調 OpenKore；本作玩家是來讀故事與做抉擇的，3～4 條準則已足夠，再多會把樂趣從判斷移到調參。
- **用重複刷怪支撐排行與活動**：與一次性案源衝突，game-design 已排除。
- **開放市場與 Zeny sink 的稅制調校**：ro-idle 光擺攤稅就改了兩次；本作首版沒有交易，不需要這套。

## 6. 若要採用，建議的下一步

1. 在前兩案的試讀稿中，為每個方案寫出 §3.1 式的理由行，檢查理由是否只有能力門檻。
2. 在 risk-systems 的狀態表中加一欄「死因敘述需要的資料」，確認伺服器結算時有保存。
3. 由使用者決定 §4.5「系統錯誤致死」採 (a)／(b)／(c) 哪一種，再寫進 risk-systems；architecture 補「舊分頁被接手的通知」一項。
4. 再補一次實測：在沒有其他遊戲分頁開著的情況下離開 3 分鐘以上，看離開期間報告的實際畫面（研究文件 §10）。
