## 1. 技術選擇

使用者已指定React與Cloudflare、允許shadcn/ui與Tailwind。手機直式為主要交付介面，電腦相容。具體基線為React＋TypeScript＋Vite、shadcn／Tailwind、React Router與TanStack Query，Workers＋Hono API、D1遊戲狀態、頻道DO聊天。詳細分層、目錄、API、版本與交易設計見 [架構](architecture.md)，手機元件與tokens見 [UI系統](ui-system.md)。

選擇理由是本作主要處理文字閱讀、清單、跨裝置狀態與時間到期結算。原生網頁直接使用 DOM／CSS，能自然支援響應版面、文字選取與鍵盤操作。已查看 godot-kit；其 Godot 模組不直接移植到此 TypeScript 專案，沿用測試與資料權威原則即可。

官方依據（2026-10-29 查閱）：[React＋Vite](https://developers.cloudflare.com/workers/framework-guides/web-apps/react/)、[Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/)、[D1 batch 交易](https://developers.cloudflare.com/d1/worker-api/d1-database/)、[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)、[Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)。文件支持產品能力；本作容量與成本仍須實測。

```text
手機／電腦瀏覽器
       │ HTTPS：指令、狀態查詢
       ↓
Workers：登入驗證 → 任務規則 → 到期結算
       │                         ↑
       │                   定期批次補結算
       ↓
D1：生死／角色／一次性案件／獎勵／事件／排行
       │ 已提交的廣播事件，重試與去重
       ↓
頻道Durable Object ← WebSocket → 公共聊天／系統廣播

版本化內容資料 → 伺服器規則 → 可閱讀的結果與故事
```

遊戲指令仍用HTTP與伺服器同步，聊天使用WebSocket；城市／排行可見時低頻查詢，背景停止輪詢。每個頻道一個DO，聊天保存在頻道儲存，生死與經濟權威留在D1。系統廣播從D1已提交的outbox推送、以event_id去重，廣播延遲不改變遊戲結果。暫不引入Queues、KV與R2。

通訊官方依據：[WebSocket與Hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)。這支持聊天室建議，不是本作已做過負載測試的證據。

新專案暫以 `prototypes/tokyo-text-mmo/` 為代號，正式遊戲名未定。建立專案時鎖定套件、工具版本及lockfile，不把generator source根目錄改成單一遊戲專案。

## 2. 模組與資料邊界

| 範圍 | 責任 |
|---|---|
| 介面 | 顯示、表單、倒數、閱讀與無障礙；不決定獎勵 |
| 規則函式 | 任務方案、生命狀態、救援、通緝、抗性／負荷／壓力、解鎖與報酬；可注入時鐘 |
| API／登入 | 驗證玩家身分與指令、限流、取得或修改狀態 |
| 資料庫 | 每角色案件唯一性、一次性結算、生命終態、角色所有權、城市進度與週分數 |
| 聊天頻道 | 訊息持久化、排序、補讀、限流與禁言；不持有遊戲狀態的第二份權威 |
| 內容資料 | 任務、裝備、故事、區域、初始平衡值；保留內容版本 |

核心資料：users／sessions、characters（生命狀態與生涯ID）、owned_items、mission_runs、story_state、reward_ledger、medical_coverage、medical_claims、city_events、event_contributions、weekly_scores、notification_outbox。頻道獨立保存messages與管理狀態。依工作包逐步建立，不導入通用ECS或完整事件溯源框架。

內容資料建議使用有 schema 的 JSON；故事節點分為敘述、條件、選項、效果與結尾。先用文字檔維護，不先開發視覺化任務編輯器。建置檢查 ID 重複、缺少引用、斷路與不可達結尾。

## 3. 自動委託與離線

開始時由伺服器確認角色存活、資格、資源、空閒狀態及該角色尚未消耗此案，保存方案、裝備、保障與內容版本、開始及到期時間。每角色只允許一份進行中委託；案件以character_id＋quest_id限制重接，新角色使用新ID。

自動流程到期，由同步請求或定期工作推進至下一個安全段／等待節點／結尾，不能在背景越過致命節點。安全結尾一次提交結果與收益；危險節點確認則一次判定該段結果、救援與生命狀態。具體規則見風險系統。定期工作確保已完成成果即使玩家未回來也能進入城市進度；等待選擇則不再推進。

```text
閒置 → 接取獨立案件 → 自動段 → 危險節點等待
                                   ↓ 玩家選擇
                         生還／救援／死亡的一次性判定
                                   ↓
                         下一段／結案／永久終止

故事到達選擇點 → 等待玩家 → 保存選擇 → 下一個故事節點
```

瀏覽器倒數只是顯示；改本機時間、關分頁、重整都不改變結果。首版不採每秒更新角色的背景工作，也不以瀏覽器 timer 作結算權威。

### 必須證明的資料一致性

- 同時按兩次開始：只能成功建立一份進行中的案子。
- 同角色重接已完成、失敗或撤離的案件：拒絕；新角可獨立接取。
- 同一任務由重連、雙分頁與排程同時結算：只能發獎一次。
- 重試一個已提交的故事選擇：回傳同一結果，不能重領獎勵。
- 任務途中改裝或內容更新：原任務仍依快照與原內容版本結算。
- 不同玩家同時貢獻：事件進度不遺失；開路獎勵或里程碑只生效一次。
- 危險節點重送／雙裝置選不同方案：只能選一次，不能重抽生死結果。
- 死亡與領獎／升級／救援同時抵達：依固定事件順序與角色版本交易處理；死亡終態不能被治療更新回存活。
- 死亡後舊session／舊WebSocket不能再以該角操作遊戲；新角不繼承裝備與分數。聊天身份政策需明示。
- 系統廣播先持久化遊戲事件再送達，重試不能重廣播或重發獎勵。
- D1 batch 具回滾能力，但「條件更新沒有改到資料」不一定會拋錯；必須以唯一鍵、受同一結算憑證控制的 SQL 與條件限制，讓未取得結算資格的請求完全不加獎勵。不能先讀取判斷，再無條件寫入。

使用單一 D1 交易維護相關資料，不把城市進度放到另一個最終一致儲存。SQL 與並發驗證在 M2 完成；這份文件不是已驗證的 SQL 實作。

## 4. 帳號、排行與事件生命週期

封測建議採單一第三方登入供應者，在M0固定。伺服器session cookie代表帳號，當前生涯是另一個ID；一帳號一個活躍角色，死亡角色留檔後可建新角。M1的本機角色明示為開發切片，不當作正式帳號或真實排行。生命狀態、聊天資格與角色所有權由伺服器驗證。

事件有 draft／active／completed 狀態；門檻在啟動時保存。測試世界與正式世界分開，管理重置需明示並留下記錄。首個城市事件沒有截止期限，完成後路線永久開放；日後限時事件另立規則。

週榜保存week_id與每份任務計分紀錄，不能藉延遲回報搬分。週界線後先進入closing，分批結算截止前已完成的案件，再轉closed；等待玩家的節點不算已完成，截止後才確認並完成的結果歸新週。具體權重及跨週起訖案例在M0決定並以M4測試固定。

每角色只有一次性案源，M0需重新固定章節／進度分組、案件權重與週分歸屬，不沿用重複委託的每日刷分設計。死亡角色保留已取得成績並標示狀態，新角色不可合併繼承。新角重玩對城市事件的貢獻需定帳號範圍上限，避免故意送死重刷事件獎勵。週榜規則未完成前，相關工作包不能標為Ready。

## 5. 首版範圍

依玩法與文本計畫：2區、2名中間人；先6件一次性案件切片，再擴到24案封測；9件固定裝備、角色等級與抗性、警方0～5星、永久死亡及條件救援、1件三目標城市事件、公共聊天及系統訊息、名聲生涯紀錄及後續週榜。一帳號一活躍角色，死亡後可重建。

24案是封測內容目標，不代表足以支撐數月營運。首版不做真人即時組隊、私訊／語音、公會、PVP、交易／拍賣、抽卡、付費、重複刷案、AI即時生故事或大型內容編輯器。聊天與系統訊息已是首版需求。

## 6. 階段與完成條件

依賴順序M0→M1→M2→M3→M4→M5。先驗證生存風險與恢復，再大量寫案；M1規則函式在M2由伺服器調用，不重寫第二套判定。

| 階段 | 交付物 | 完成證據 | 粗估工作量 |
|---|---|---|---|
| M0：風險與文本基線 | 前兩案、生命／救援／通緝／抗性狀態表、內容schema、有限經濟、計分與登入方案 | 可手算生還、救援失敗、永久死亡與新角重玩；作者試讀 | 2～4人日 |
| M1：風險可玩原型 | 案件自動段、危險等待、三種解法、等級抗性、警方與救援、本機生涯 | 一份獨立測試案走通生還／搶救／死亡，新角可重玩；正式劇情無強制試死 | 4～7人日 |
| M2：權威與恢復 | 登入、D1生死交易、一次性案源、保障帳單、跨裝置、離線節點 | 死亡不被舊請求覆寫、雙選項只選一次、重連不重抽；有限資源路線不軟鎖 | 4～7人日 |
| M3：通訊 | 公共聊天、系統廣播、補讀、限流、禁言與來源標示 | 兩帳號聊天，斷線補讀不重複；玩家不能冒充系統；廣播重試與死亡身份一致 | 3～5人日 |
| M4：城市與排行 | 一次性案件貢獻、區域開放、名聲生涯榜與週榜 | 兩帳號共同達標、新角不能濫刷事件獎勵、已死角色留榜、跨週正確 | 4～7人日 |
| M5：內容與封測 | 先6案，再24案；分支、治療經濟、手機與恢復、封測說明 | 作者走讀各條可達路線、確認前30分鐘及死亡規則；再跑完整適用suite | 4～6人日，不含大量撰稿 |

程式與整合粗估21～36有效人日，信心低，非日曆交期或AI時數。另有24案約3.1～5.6萬中文字元的撰寫、審稿與走讀，不能包含在上述程式估算；先完成前兩案量測，再估內容交期。原12～20人日估算不再適用。等待試玩、帳號設定與新增需求另計。

## 8. 驗證策略：最低充分證據

- 規劃層：這輪不跑程式測試。實作時才建立相應檢查，不把文件數量當完成遊戲的證據。
- L1：任務判定、等級抗性／負荷、醫療到達／生存窗口、通緝、生命轉移、故事效果及內容引用，用Vitest等工具驗證。
- L2：死亡與救援競態、一次性案源、危險等待、登入、跨裝置、D1交易、聊天DO／WebSocket、outbox、事件並發與跨週；使用對應runtime測試環境，外加少量Playwright冒煙。
- L3：本作跨系統封測里程碑，先做作者手動驗收，再跑完整適用 suite。過程中只跑變更涉及的 L1／L2。
- 手機直式優先：檢查360／390／430px寬、Safe Area、軟鍵盤聊天、長文、生死選項、重整／背景回來與錯誤重試；真人iPhone Safari閱讀與恢復另記證據。電腦相容與鍵盤操作列次級驗收，不取代手機證據。
- M2驗證生死與重送，M3驗證頻道與重連，M4驗證共同結算熱點；不以100個角色資料冒充100個真人同時在線。正式永久死亡案例用隔離測試生涯驗證，不污染玩家角色。

每個工作包回報測試層級、確實執行的指令、結果與未驗證範圍。完整測試的腳本名稱在建立專案時寫入該遊戲 README，現在不虛構已存在命令。

## 9. 容量與成本如何驗證

封測先以10～30名受邀玩家觀測，尚非容量保證。M3／M4以100個模擬session分別量測聊天連線與遊戲負載，記錄延遲、錯誤、SQL時間、訊息扇出、DO活躍時間及工作積壓，再決定是否擴大。

例如 100 名玩家都前景顯示城市面板，30 秒同步一次，就是約 12,000 次請求／小時，還不含接案與個人狀態。實作先共用一次狀態同步，避免每個元件各自輪詢；非必要面板不查詢。

D1 單資料庫依序處理查詢，不能以 Workers 可擴展就推論共享寫入無上限。事件加總須有索引與有界工作量。若監測到熱點，再比較減少查詢、分批處理或改變儲存拓撲，不能未量測就承諾萬人服。[官方限制](https://developers.cloudflare.com/d1/platform/limits/)

本輪不報月費數字；建立測試環境時再以當日方案、請求、讀寫、聊天連線與訊息量估算，設定可觀測用量上限。初期不預設遊戲內AI推論成本。

## 10. 風險與處理順序

| 風險 | 在哪個階段解決 |
|---|---|
| 自動執行只有等待、沒有選擇感 | M1 先比較配裝與解法；不滿意就改規則，不先堆任務 |
| 一次性文本量與分支膨脹 | 先兩案測製作速度、再6案走讀；24案分批交付，短後續匯流但保留人物記憶 |
| 死亡與救援不同步、舊請求復活 | M2先證明生命終態與並發一致性，再開放真人風險 |
| 有限任務導致缺錢／缺名聲軟鎖 | M0與每批內容盤點各條路線的恢復費、保單與進度門檻 |
| 玩家太少或案源有限導致事件卡住 | 測試世界低門檻；按有限貢獻總量設定正式門檻 |
| 新角刷事件與週榜案源不公平 | M0定帳號事件上限及分組；M4驗證，不重刷原案補洞 |
| 玩家發言冒充系統、訊息漏送 | M3來源驗證、限流／禁言與outbox重試 |
