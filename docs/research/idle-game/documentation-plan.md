# 文件製作計畫

本次已寫研究包、30份系統草案、架構／數值／roadmap；下列正式文件是**新遊戲進入製作時的預定產物**，尚未建立。路徑相對於未來該遊戲根目錄。沒有替 generator source 建立遊戲級設定。

## 1. 文件類型與內容契約

| 代號 | 正式產物 | 必寫內容 | 撰寫／驗收責任 |
|---|---|---|---|
| B | `design/game-brief.md` | 玩家幻想、桌面使用情境、核心循環、設計支柱、目標平台、MVP邊界 | Lead Game Designer／作者 |
| G | `design/gdd/<system>.md` | 概述、玩家價值、詳細規則、公式、例外、依賴、調參、驗收；標示需求ID | Lead／Systems Designer |
| F | `design/balance/<system>.csv`及公式說明 | 變數、單位、疊加順序、上下限、範例、分布、時間成本、來源 | Systems Designer |
| U | `design/ux/<screen>.md` | 資訊層級、互動狀態、空／滿／鎖定／錯誤、鍵鼠、一般視窗縮放、字級與無障礙 | Lead Game Designer＋UI責任人 |
| T | `docs/technical/<system>.md` | 責任邊界、輸入／輸出、資料擁有者、command／event、scene契約、儲存欄位、錯誤處理 | Lead Programmer＋Godot Specialist |
| D | `data/schema/<system>.json`及樣本資料 | 穩定ID、型別、必填、約束、參照、版本、合法及非法範例；編輯器Resource對照 | Lead Programmer＋Systems Designer |
| Q | `tests/plans/<system>.md` | 正常、邊界、失敗、存讀、重入／重複請求、與其他系統整合；測試資料 | 設計與程式共同定義驗收 |
| A | `docs/adr/<number>-<topic>.md` | 技術問題、候選方案、選擇理由、後果、驗證與回退；狀態從Proposed開始 | Lead Programmer／作者核定重大選擇 |
| C | `design/content/<kind>.csv` | 實際角色、怪、技能、裝備、配方、關卡列表及資產ID；不是只有資料結構 | Systems Designer |
| E | `production/evidence/<milestone>/` | 建置識別、環境、指令、log、錄影／截圖、測量結果與未通過項 | 整合與最終驗收者 |

每個數值規則的GDD都要有F；不是數值系統的桌面殼也要定義尺寸、容許誤差與失敗規則，但不必造一張戰鬥數值表。目前製作範圍內的系統要有T與Q；S03的桌面專屬文件隨系統延期；沒有獨立畫面的系統可共用U，避免30份重複版面文件。

## 2. 逐系統需要哪些文件

30份草案各自的「文件交付」節列出G／F／U／T／D／Q／C需求。以下規則補足文件間關係：

- S01統一定義D與內容C格式；各系統補自己的欄位和樣本，不各自發明ID規範。
- S02、S08、S09、S10共用戰鬥事件契約；分別負責時序、扣血、技能意圖、反應規則。
- S05、S06、S11～S16共用角色詳情U；各系統清楚標示屬性來源、解鎖與預覽。
- S17、S18、S21共用交易契約；製作、獎勵和搬移都必須有滿包與回滾規格。
- S23維護完整存檔schema、版本遷移表與fixture；其他T文件列自己擁有的欄位。
- S24若不納入產品，仍須在B和S02寫明關閉／睡眠的收益政策；不能留給執行時自行猜。
- S27、S30跨系統適用；UI、聲音、特效與效能預算要能追溯到相同設定值。

## 3. 建議的ADR清單

| ADR提案 | 要解決的決策 | 決策時間 |
|---|---|---|
| A01 桌面視窗整合（Deferred） | S03恢復時再定平台／視窗能力；目前用一般Godot視窗 | 未排入目前里程碑 |
| A02 模擬權威與時鐘 | 固定步長、事件順序、RNG分流、睡眠補算、畫面與邏輯分離 | M1前 |
| A03 資料與內容來源 | Resource／JSON分工、ID版本與驗證、定義不可變 | M1前 |
| A04 存檔與交易 | 快照、備份、跨系統原子更新、遷移、重複結算去重 | M2前 |
| A05 關鍵詞事件處理 | 同幀死亡／治療、反應限制、過量治療、觸發來源標記 | M3前 |
| A06 離線模型 | 是否支援、固定關卡、收益上限、模型誤差與領取語意 | M3前 |
| A07 長期數值表示 | 64位整數／定點／浮點的範圍，何時需要大數格式 | M4內容擴張前 |

以上均為Proposed，沒有偽裝成已Accepted。GDD未定的玩法不藉由ADR偷偷決定。

## 4. 文件生產與檢查順序

```text
證據紀錄 → Game Brief／範圍 → Systems Index
                                  │
              ┌───────────────────┘
              ↓
       GDD＋數值表＋UX → 技術規格＋必要ADR
                                  │
              ┌───────────────────┘
              ↓
      資料樣本＋QA案例 → Epic／Story → 實作 → 驗收證據
```

G、F、U可以交錯修訂；不要求先寫完所有30系統才能做M1風險測試。每次只完成下一個里程碑需要的細節。現在的研究草案不等於已完成每個系統的正式GDD、F資料表或可實作story。

## 5. 實作就緒檢查

一個系統能交給工程師前，必須有明確輸入／結果、可計算的規則、至少一筆合法資料、失敗行為、持久化政策、已解決的必要決策、可測的驗收，以及最小可編輯scene清單（若有畫面）。

需求追蹤用 `SYS-S08-001 → GDD段落 → 技術契約 → Story → Test → Evidence`。每個系統草案的 `AC-Sxx-*` 是驗收草案ID；建立正式需求時再分配TR-ID，不假稱已通過Studio traceability gate。
