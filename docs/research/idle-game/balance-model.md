# 數值與經濟模型草案

除明確標O者，本文件全部為P範例，供原型建模；不是原作逆向公式，也不是已核定的遊戲平衡。百分比以小數儲存，顯示時再轉換；中間計算保留精度，最終結果才按規則取整。

## 1. 屬性與攻擊

```text
基礎成長＋裝備固定值 → 性格 → 加算百分比 → 獨立倍率 → 上下限
                              │
                              └→ 來源明細＋最終值 → 攻擊／技能
```

`A = (A_base + A_flat) × personality × (1 + sum(add_pct)) × product(more_mult)`。

A單位為攻擊點；原型A_base建議測1～1,000，固定加值≥0，倍率不可小於0。例：10基礎＋2裝備、勇敢對該屬性1.10、10%加成，A=14.52；若顯示四捨五入為15，不應把15再拿回核心重複取整。性格若作用於不同屬性，其倍率分別儲存。原作E02的±10%只作O證據，不代表自製版每種性格都要照搬。

`D = max(1, floor(A × skill_coefficient × type_multiplier × crit_multiplier × (1 - resistance)))`，只在明確定義的傷害事件使用；免疫可特例為0。原型抗性範圍先鎖0～0.75，crit機率0～0.5，暴擊倍率1～2.5，全部為測試護欄；不同傷害型態是否共享護甲須在S08決定。

`interval = max(interval_min, base_interval / (1 + haste))`。base_interval單位秒，原型0.5～3，haste 0～2，interval_min先用0.15測壓力。這是一個候選公式，不能用E03的`1.56 (1.40)`反推原作加速規則。

`single_target_DPS ≈ expected_damage / interval + skill_DPS`只用來做近似比較。實際收益需計入接敵、溢出傷害、治療停手、敵人抗性與死亡重試。

## 2. 治療與反應

E04可見2.4A及12秒冷卻。P範例取A=12，`H_raw=2.4×12=28.8`，UI取整29；這只說明範例相容，並未證明原作完整公式。

自製原型建議 `H_applied=min(missing_hp, H_raw)`，治療觸發傷害先依實際治療計，`D_react=floor(H_applied×0.5×reaction_multiplier)`。例：只缺10HP，得到10治療，基礎反應傷害5；0有效治療不觸發。E08原文提到「治療基值」，因此此提案可能與原作不同，必須保留raw/applied兩欄供核定。

`stack_multiplier = 1 + min(stacks, stack_cap) × stack_bonus`。原型stack_cap=3、stack_bonus=0.03僅用於驗證UI和上限；buff時長用模擬tick，不依動畫完成。反應事件帶cause_id與tag；同源不能重入同一規則，每原始事件最多8層／64個子事件，觸頂須記錄診斷。上限是保護，不應成為正常build的傷害來源。

## 3. 羈絆與隊伍

建議只計上陣、不同物種的有效成員，門檻取最高階、不累加前一階；死亡是否保留計數先採整場build鎖定。這三項全為P，原作尚未確認。

例：2個不同精靈啟用+10%攻擊，3個啟用+18%攻擊且取代前者；同物種重複上陣不追加計數。原型只需2種種族、2種屬性、3個上陣格即可驗證張力。任何slot加成從S20進入SlotPolicy，再由S11使用，不能在兩處各加一次。

## 4. 經驗與解鎖

候選每級所需經驗 `XP_next(L)=round(100×1.25^(L-1))`，L先測1～20；1→2需100，2→3需125，3→4約156。大額經驗須while迴圈跨多級並保留餘額。E03原作1級1000經驗與此提案分開。

天生詞綴使用門檻陣列；E01／E03可讀到10、25、40、65、80、100等門檻，原型縮成3、5、10測解鎖頻率。進化保留哪些數據另定；更換基礎模板後重算，不在舊值上反覆加成。

## 5. 收益、掉落與容量

`gold_per_min = kills_per_min × mean_gold_per_kill × uptime`。例：12擊殺／分、平均3金／隻、存活率0.9，為32.4金／分。應比較不同獵場的實測收益，而不是只以最高關卡排序。

`expected_drop_count = kills × drop_probability`，`P(at least one)=1-(1-p)^kills`。p=0.01時，100次至少一次約63.4%，不是100%。保底、重複保護、閃光機率均未由素材確認；自製若採用必須獨立定義，不能暗加。

滿包原型提案：金幣／EXP直接進帳；實物進有界的待領箱；待領箱也滿時停止接受實物並顯示持續告警，保留戰鬥與其他收益；不自動刪稀有／鎖定物。上限及通知頻率由S17定，離線模型沿用同政策。

## 6. 成本、進化與工坊

候選天賦成本 `C(k)=ceil(C0×r^k)`，k為已買等級，C0先測20、r測1.2～1.8。第一次20，r=1.5時後續30、45、68。不要在未觀測收益前把曲線定死。

可比指標 `payback_minutes = cost / (income_after - income_before)`，差額≤0時顯示無直接收益而非負回收期。升級可能帶來存活或收藏收益，不能全強迫換成金幣。

進化配方先採資料化：主體UID＋N個符合條件的素材UID＋gold。N、稀有度與是否同物種需作者決定；交易預覽清楚列出保留及消耗。以N=2的測試fixture驗證安全，不把N=2當既定設計。

工坊若每次消耗cost、成功率s、成功產一件且失敗全損，期望成本是cost/s；若保留部分材料則重算。跨階率u條件於成功時，總機率為s×u。E09只顯示100%／2%，不足以判定兩次判定是獨立還是條件式。

## 7. 離線收益候選

`elapsed=clamp(now_utc-last_reward_watermark,0,cap_seconds)`；MVP先不支援離線戰鬥補算，但要保存watermark、明示關閉後暫停。若在M3開啟S24，cap先用8小時作待測P，僅對最後可穩定通關的已解鎖獵場與凍結build估計。

`offline_gold=floor(rate_at_snapshot×elapsed/60×efficiency)`。例：32.4金／分、60分鐘、效率0.8，1555金。rate與efficiency須先由批次模擬校準，不能由UI最近一秒跳字直接決定。原型要求相同build／關卡與多seed平均在線結果相差≤10%；非保證對所有隊伍都成立。

領取以`receipt_id、interval_start、interval_end、model_version、summary`原子記帳；已結算區間不得再以在線catch-up或另一視窗領一次。休眠／關窗採互斥時間區間；讀到時鐘倒退給0並前移政策受控，不使用絕對值補獎。

## 8. 平衡資料與實驗

至少產出角色基礎表、EXP曲線、技能係數／冷卻、效果疊加、敵人曲線、掉落表、天賦成本、進化配方、工坊配方、關卡收益與解鎖節奏11類表。每筆含ID、單位、公式來源、版本、測試範圍。

M2先測100個seed×每組10分鐘，比較生存、擊殺、金／分、EXP／分、滿包時間；M3加入純輸出／治療反應／羈絆隊伍，每個build同內容版本與seed集合。這是預定實驗，現在尚未執行遊戲平衡測試。
