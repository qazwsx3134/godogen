# 《消失的草莓牛奶》：2D 第一人稱互動小說 Roadmap

更新：2026-09-16。已確認：2D 主觀視角、先完成短篇再整理工具，從 `docs/gintama-like/` 與現有 `prototypes/missing-strawberry-milk/` 開始。功能與體驗目標依各輪測試驗證。

目前進度：**P0 的功能基線已通過，真人試玩待執行；P1 起的 2D 改編仍為待實作規格。**

## 1. 要做出的成果

**讓擅長寫作與畫畫的朋友，把自己的文本與插畫做成一篇可以交給別人玩的故事，並能持續自己修改。**

第一個故事使用銀魂角色與現有《消失的草莓牛奶》文本。朋友可以先參與這篇的改稿、分鏡與繪圖，再用完成短篇時驗證過的流程製作後續故事。

產品有兩個互相配合的部分：

- **故事播放端**：玩家以主角的視角觀察場景、閱讀、回應角色、理解線索，讓故事產生回應。
- **創作端**：作者寫段落、安排選項、放入插畫與互動物件，立即試玩自己的內容。

執行順序：**測試現有草莓牛奶雛形 → 第一人稱場景與調查互動 → 短篇試玩與修正 → 整理作者工具 → 下一篇驗證重用。** 創作流程從第一段就開始記錄，短篇完成後再集中整理工具。

## 2. 流程定位

依新增的 `game-dev-process.skill`，目前處於**已有文字雛形的前期製作**。本輪先取得可重現的功能測試結果與真人試玩紀錄，再決定下一個原型改動。測試採「先跑通流程，再驗收基調，再擴大試玩」的順序。

本案把 skill 的查核落成三個問題：

1. **創作可行性**：朋友願不願意用這個方式改編作品？一個場景的文本與美術需要多少時間？
2. **體驗可行性**：觀察、選擇、解謎是否讓玩家更投入人物與故事？
3. **技術可行性**：能否穩定播放分支、呈現圖像，讓作者預覽並交付可玩版本？

本階段的資源目標是雙人可持續投入與小規模試玩。商業化方式待有首次可玩版與回饋後決定；正式 GDD 與架構文件再依驗證結果撰寫。

## 3. 結合銀魂概念的方式

| 來源 | 採用概念 | 草莓牛奶短篇中的落點 | 要觀察的結果 |
| --- | --- | --- | --- |
| [chat-1.md](../gintama-like/chat-1.md) | 日常小事被當成大危機；普通事件逐步失控 | 牛奶不見 → 詢問嫌疑人 → 發現黑影；先使用明確劇情觸發失控 | 玩家是否理解荒謬是如何一步步升高的 |
| [chat-2.md](../gintama-like/chat-2.md) | 人物關係、反覆出現的笑點、選擇累積後果 | 記住先問了誰，讓對方在黑影出現或收尾時回嘴；先在同一短篇內完成一次呼應 | 玩家是否察覺「他記得我剛剛做的事」 |
| [chat-3.md](../gintama-like/chat-3.md) | 先測文字是否好笑，再測吐槽；以《消失的草莓牛奶》做原型 | 從現有詢問分支、兩秒吐槽、成功／失敗收尾取得基線 | 是否願意讀完、是否懂吐槽、是否想試另一種選擇 |
| [story-prompt.md](../gintama-like/story-prompt.md) | 固定角色視角；荒謬日常 → 失控 → 吐槽／反差 → 喜劇收尾 | 銀時主觀視角、其他角色各有喜劇功能；黑影與錯棚笑點沿用既有種子 | 玩家是否知道自己是誰，且能說出一個有效笑點 |
| [chat-2.md](../gintama-like/chat-2.md)、[chat-3.md](../gintama-like/chat-3.md) | 利用已知資訊理解事件 | 用看過的物件細節辨認真正的牛奶盒，讓新資訊打開新回應 | 玩家是否能說明推理依據 |

首篇的互動組合是**閱讀 → 調查／詢問 → 發現不合理之處 → 吐槽 → 角色回應 → 喜劇收尾**。時間輪迴、不同類型的小遊戲與長期關係成長，作為短篇通過後可另立假說的題目。

### 核心體驗與第一篇規模

「沉浸」的初始假說：玩家有明確身分，能決定注意什麼、相信誰、如何回應；畫面、文字與聲音共同呈現這些行動的後果。

```mermaid
flowchart LR
    A[進入主角眼前的場景] --> B[閱讀與觀察]
    B --> C[點擊物件或與角色交談]
    C --> D[取得線索或理解人物]
    D --> E[推理或作出選擇]
    E --> F[對話與場景回應]
    F --> B
    F --> G[短篇收尾]
```

### 內容預算

| 項目 | 第一篇上限／目標 |
| --- | --- |
| 首次遊玩 | 約 10–15 分鐘，以實際閱讀與互動時間調整 |
| 空間 | 1 個主要地點、最多 3 個場景畫面；可包含同一空間的特寫 |
| 人物 | 玩家視角建議銀時；沿用新八、神樂、房東與神秘黑影。立繪優先新八／神樂，房東可先文字登場，黑影用剪影 |
| 觀察 | 約 3 個有敘事意義的可點擊物件 |
| 選項 | 約 3 次重要選擇；至少 1 次後續明確回應先前的決定 |
| 解謎 | 改編版加入 1 個從文本／插畫取得線索的推理問題，可重試並取得提示；現有雛形先測詢問與吐槽 |
| 分支 | 1 條主線，局部分支回合流，最後 2 種有差異的收尾 |
| 美術 | 初期使用朋友已有素材或草圖；首次可玩版完成 1 個代表場景的視覺品質，其餘保持可讀 |
| 聲音 | 視內容需要加入 1 段環境音與少量事件音效；文字可完整傳達關鍵資訊 |

### 第一篇的故事節拍

| 節拍 | 目前雛形 | 2D 主觀視角改編規格 |
| --- | --- | --- |
| 牛奶不見 | 銀時把牛奶稱為「江戶最後一滴正義」 | 玩家面對冰箱，透過內心文字與新八的回應知道自己是銀時 |
| 選擇詢問 | 新八／神樂／房東三選一，各有一小段對話 | 保留三位對象；角色向玩家回應，記錄先問了誰 |
| 日常升溫 | 白色痕跡、可疑空盒、房租催繳 | 把對話裡可觀察的物件做成點擊特寫，區分笑點與可靠線索 |
| 黑影登場 | 走廊黑影、斗篷、馬賽克與錯棚對話 | 使用走廊場景與剪影，做一次敘事上的失控 |
| 推理／吐槽 | 三句吐槽，兩秒內選擇；未選也有後續 | 推理建議：由盒身記號辨認真正的牛奶，取得資訊後可作出有依據的回應；吐槽時限依基線回饋調整 |
| 收尾 | 成功拿回牛奶；失敗則決定去超商 | 保留兩種喜劇收尾，加入先前詢問對象的一句呼應 |

表中「2D 主觀視角改編規格」是下一輪待實作內容。現有故事檔維持為可比較的文字基線。朋友先參與修改一段對話與一個收尾，觀察創作交接的成本。

## 4. 里程碑總覽

下列時間是**規劃用工程工作日範圍**，以現有 Vite 原型、2D 草稿素材與單一內容格式估算。P0 先測基線；P1–P3 的改編與試玩約 7–11 日；P4 整理作者工具再估 3–5 日。另加作者創作、試玩安排與修正時間。

| 階段 | 要回答的問題 | 可檢視的產物 | 時間盒 |
| --- | --- | --- | --- |
| P0：測試現有雛形 | 分支跑得通嗎、文本與兩秒吐槽成立嗎？ | 建置／12 條流程／瀏覽器測試結果，加第一輪真人回饋 | 功能檢查半日；5 人各約 15–20 分鐘試玩與訪談 |
| P1：主觀視角與演出 | 從銀時眼前閱讀與回應，是否有代入感？ | 現有開場與詢問的 2D 場景版；朋友的一段改稿與草圖 | 2–3 日 |
| P2：完整敘事循環 | 觀察與選擇是否改變故事體驗？ | 10–15 分鐘粗版、1 個謎題、條件回應、2 種收尾 | 3–5 日 |
| P3：改編短篇試玩 | 玩家能順利玩完，並感受到銀魂式互動嗎？ | 統一演出的短篇、存讀進度、分享產物、對照基線的試玩紀錄 | 2–3 日 |
| P4：作者工作流 | 她能否自己修改與預覽？ | 從首篇需求整理的內容模板或小型編輯介面、錯誤提示、可匯出的作者專案 | 3–5 日 |
| P5：製作器決策 | 這套流程能否支援下一篇？ | 用相同功能做出的另一段 3 分鐘故事與缺口清單 | P4 通過後另估 |

P1 → P2 → P3 先交付短篇，P4 再整理製作工具。每一階段都讓朋友參與編改內容；首篇期間以模板與技術協助保持創作進度，同時記錄重複操作與卡點。每個時間盒結束都交付可試玩的結果與觀察；未達標先修正或縮小該階段。

## 5. 各階段工作與通過條件

### P0 — 測試現有草莓牛奶雛形

**功能基線**：執行建置，覆蓋三位詢問對象 × 三句吐槽／逾時的 12 種輸入；核對收尾與 Flag，檢查重開清除狀態。瀏覽器另外測真實點擊、兩秒計時、結束與重新開始。

**真人試玩**：依 [PLAYTEST.md](../../prototypes/missing-strawberry-milk/PLAYTEST.md) 讓 5 人首次盲玩，記錄看不懂的地方、笑點、吐槽閱讀壓力與是否願意重玩。先讓朋友自行改一段台詞，由使用者協助放入原型，記錄步驟。

**通過**：功能測試沒有阻斷流程的問題；真人能理解「牛奶不見、調查、黑影、吐槽、收尾」。吐槽與閱讀節奏的問題有具體紀錄，可用來指定 P1 的修正。程式通過與體驗通過分開記錄。

### P1 — 把現有開場改成銀時的主觀視角

**播放端**：以現有 `intro → choice_suspect → suspect_*` 為第一段，加入場景圖、人物圖與銀時內心文字，保留點擊繼續、詢問對象與角色回應。一般閱讀與詢問由玩家自行推進；兩秒吐槽依 P0 回饋決定是否製作無時限對照版本，兩種版本的結果各自記錄。

**創作端**：從第一版就把文本與素材放在明確的內容入口；朋友照一份範例換掉一句話與一張圖，能看到自己的版本。初期可由使用者協助匯入、啟動預覽，記錄所有協助。

**試玩**：請 3 位未讀過文本的人試玩，觀察能否自行推進；結束後問「你扮演誰、想做什麼、對方對你的決定有何反應」。

**通過**：3 人都能操作到結束，至少 2 人能說明身分與眼前目標；朋友能完成一次改稿預覽。若文字與畫面讓人困惑，先調整視角、排版、段落與演出。

### P2 — 讓線索、選擇與後果接起來

**播放端**：加入可點擊物件、物件特寫、已知線索列表、少量故事狀態、條件對話／選項、謎題提示與重試、兩種收尾。

**故事規則**：觀察物件獲得線索；取得線索後能提出新問題；`asked:*` 在黑影登場或收尾時產生對應回應。必要線索可再次查看；線索列表只收錄玩家已知資訊。分支回合流時仍保留先前選擇的後果。

**創作端**：朋友填出每個物件的描述、取得的資訊、解謎提示、分支條件與收尾；每完成一段就預覽。這一階段確認她理解「何時出現／選了以後會發生什麼」的編輯方式。

**驗證**：逐條跑過設計內的選項、線索取得順序、答錯與重試，以及兩種收尾；檢查重複點物件、返回場景是否錯誤重複發放結果。由 3 位試玩者評估推理依據是否清楚。

**通過**：所有設計內路徑可結束；沒有因探索順序造成的卡死；至少 2 位試玩者能指出自己的行動影響了哪一句回應，並在一次內建提示內完成謎題。若大家都靠猜答案，先修線索與提示。

### P3 — 試玩並交付改編短篇

整合一個代表場景的美術與演出品質，統一文字樣式與畫面切換。補齊文字回顧、字體／聲音基本設定、重新開始、單一自動存檔與繼續遊玩。

**存檔驗證**：至少在取得線索後、分支選擇後各存一次，關閉重開後檢查目前段落、線索、故事狀態與後續收尾一致。改稿後的舊存檔須能辨識內容版本並明確提示是否需要重新開始。

**交付**：產出能在另一台目標裝置啟動的版本；若選 Web，產出部署檔與試玩連結流程。作者專案備份與玩家遊玩版本都要實際打開驗證。

**5 人試玩目標**：

- 至少 4 人能在無口頭引導下完成短篇；可使用內建提示。
- 至少 3 人能說出一次自己的決定與故事回應的關聯。
- 至少 3 人願意繼續下一段，並說明對哪個人物或問題感興趣。
- 至少 3 人能指出有效的笑點或角色反差，並解釋為什麼選了那句吐槽。
- 記錄閱讀時間、停止閱讀的位置、謎題提示次數，以及發生的操作問題。

這是小樣本的方向判斷，不能推論市場需求。首次可玩版的完成條件還包含：兩人共同修正測試中發現的一個問題，並重新產出可玩版本。記錄朋友獨立完成與需要技術協助的步驟，作為 P4 工具工作的依據。

### P4 — 從首篇整理作者工具

使用 P0–P3 的實際製作與改稿紀錄，優先處理反覆出現的操作與卡點，選定朋友實際願意使用的入口：既有工具的腳本模板、段落表單，或小型場景清單。若既有工具已達標，就把時間用在模板、指引與缺少的互動整合。

**必要能力**：

- 改文字、選角色／表情、替換背景與物件圖。
- 新增選項、設定結果與出現條件；可用範例複製一個現有謎題。
- 從指定段落預覽；需要先前條件時，提供「已拿到線索」等具名起始情境。
- 定位「這個選項沒有接到段落」「這張圖不存在」等錯誤。
- 儲存作者專案，關閉後重開仍可編輯；匯出內容與素材的可攜備份。

**作者驗收**：一次 10 分鐘示範後，使用者保持旁觀。朋友在 30 分鐘內完成「改一段對話、替換一張圖、新增一個選項及其回應、預覽兩條分支」，然後儲存並重開確認。她只操作選定的內容工具／模板，新增內容不要求修改播放端程式。

**通過**：四項修改正確呈現、專案可重開，過程不需要使用者接手操作。若未達標，記錄造成卡點的步驟並改善後重試。

### P5 — 用下一段作品決定製作器範圍

朋友使用相同功能，換一個情境、文本與插畫，做出另一段約 3 分鐘的故事。此段刻意使用已支援的對話、選項與物件互動，測試內容是否真的能替換。

**通過**：只修改內容與素材就能玩完；使用者沒有為新故事補上專屬程式。記錄新增段落所花的時間、仍需協助的操作、下一篇反覆需要的功能。

依證據選擇後續投入：

| 觀察 | 下一步 |
| --- | --- |
| 朋友用既有工具／模板很順，玩家喜歡故事 | 延伸內容，做第一章的設計與製作估算 |
| 朋友反覆卡在編排、換圖、條件設定 | 補上對應的圖形介面、預覽與錯誤定位 |
| 第二篇一直需要故事專屬程式 | 重新收斂工具支援的互動類型，或增加具體可重用模組 |
| 作者順利，玩家對互動反應平淡 | 先調整故事節奏、選擇的後果與探索密度，再試一輪 |

多人協作、通用插件、複雜節點圖、跨作品資產管理與多平台發布等能力，留待實際出現使用需求後另排里程碑。

## 6. 沿用現有原型的實作順序

| 元件 | 起點 | 下一個有測試依據的改動 |
| --- | --- | --- |
| 故事資料 | `missingStrawberryMilk.ts` 中既有段落、三位詢問對象與兩種收尾 | 固定主觀視角、補物件與線索、加入詢問後的呼應 |
| 敘事狀態 | `DialogueManager` 與 `ChoiceSystem` 的記憶體 Flag | 條件讀取、條件選項、可序列化的進度 |
| 呈現 | `main.ts` 的 DOM 文字介面與吐槽倒數 | 場景／立繪／物件特寫，保持閱讀控制與文字可讀性 |
| 測試 | `dev-walkthrough.ts` 與 `browser-check.mjs` | 每新增一種條件或互動，就加入對應的狀態案例與瀏覽器操作 |
| 作者流程 | 朋友提供改稿，由使用者整合 TypeScript 故事資料 | P4 再從重複操作整理模板、匯入與預覽入口 |

玩家介面改動前後使用相同故事基線做回歸；文本改稿保留版本，讓測試紀錄可以指出實際玩到哪一份內容。

## 7. 創作資料與實作邊界

朋友需要理解的最小概念是：

| 概念 | 作者看到的意義 |
| --- | --- |
| 故事 | 一個可保存、預覽與交付的作品 |
| 場景 | 主角眼前的地點／畫面，以及可互動物件 |
| 段落 | 一小段敘述、對話或演出 |
| 選項 | 玩家可以作出的回應，以及它接到哪個段落 |
| 線索 | 玩家已觀察到、可以回看的資訊 |
| 條件 | 例如「看過照片後，才能詢問照片中的人」 |
| 結果 | 選完後取得線索、改變故事狀態或前往段落 |

技術實作以現有 TypeScript 資料與播放端為基礎，遵守以下邊界：

- 文本、分支與素材引用有明確的內容入口；UI 操作交給播放端。
- 原型狀態先限制在少量真假條件與已取得的線索；每個狀態有初始值。預覽跳段使用完整的具名起始情境。
- 段落與素材使用穩定識別碼；改標題或檔名時能檢查相關引用。
- 若自製內容格式，預覽前檢查重複 ID、不存在的分支目標、缺圖、未宣告狀態與無出口段落；合法探索迴圈可以返回。
- 作者修改專案的狀態與玩家遊玩進度分開保存；在同一版本內容下，重讀存檔應重現相同故事狀態。
- 圖形編輯器與模板最後都使用同一套播放規則，讓預覽與交付版本一致。

### 現有原型的起點

[`prototypes/missing-strawberry-milk/`](../../prototypes/missing-strawberry-milk/README.md) 的程式閱讀結果：

- [`types.ts`](../../prototypes/missing-strawberry-milk/src/types.ts) 已有對話、選項、限時吐槽、結束段落，以及以 ID 連接段落的資料形狀。
- [`DialogueManager.ts`](../../prototypes/missing-strawberry-milk/src/core/DialogueManager.ts) 管理目前段落與記憶體中的 Flag；[`ChoiceSystem.ts`](../../prototypes/missing-strawberry-milk/src/core/ChoiceSystem.ts) 可在選擇後設定 Flag，再回傳下一段 ID。
- 一般條件對話／條件選項、跨開啟保留的存檔、探索與謎題模型仍需實作。
- `portrait`、`sfx` 是預留欄位；[`main.ts`](../../prototypes/missing-strawberry-milk/src/main.ts) 目前呈現文字，`effect` 也只是文字標記。
- 內容是程式內匯入的 TypeScript；作者工具、內容匯入與專案保存流程仍需實作。
- [`dev-walkthrough.ts`](../../prototypes/missing-strawberry-milk/src/dev-walkthrough.ts) 的目標覆蓋是 12 種既有輸入、預期收尾與 Flag；[`browser-check.mjs`](../../prototypes/missing-strawberry-milk/browser-check.mjs) 另外檢查瀏覽器點擊與真實計時。

實際測試結果見 [QA-BASELINE.md](../../prototypes/missing-strawberry-milk/QA-BASELINE.md) 與 [瀏覽器證據](../../prototypes/missing-strawberry-milk/qa/browser-smoke/evidence.json)。真人回饋與下一版的未實作測試見 [PLAYTEST.md](../../prototypes/missing-strawberry-milk/PLAYTEST.md)；功能測試不能證明笑點或沉浸感成立。
