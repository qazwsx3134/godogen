# 《守城英雄傳》競品研究

> 這是第一輪開局研究。後續新增了 33 張實機截圖與更完整的機制盤點，請以[完整研究報告](守城英雄傳研究/完整研究報告.md)及[Godot UI／component 規格](守城英雄傳研究/Godot-UI-component規格.md)為最新整理；[截圖圖庫](守城英雄傳研究/index.html)可直接瀏覽原圖。

研究日期：2026-10-24。實測：Windows Steam 試玩版，標題畫面版本 0.34.1，1920×1080。方法：Computer Use 實際操作開局、英雄上陣、前兩波戰鬥、城堡 Lv.1～5 與主炮教學，輔以官方商店資料及安裝目錄辨識。這是早期流程的競品拆解，不代表完成全內容或取得原始碼。

證據標記：**實測**＝本次畫面或操作；**官方**＝商店或開發者文字；**推論**＝設計解讀；**建議**＝適合自己遊戲的實作方向。沒有實測的係數不當成遊戲公式。

## 1. 最重要的設計判斷

它把「看著防線變強」做成主要回饋：英雄上陣後直接站到城堡上；城堡升級同時增加 HP、MP；Lv.5 出現木製塔架、門與新槽位。玩家的資源投入會反映在戰場外觀，而不只反映在數字表。（實測）

對同類型遊戲而言，最值得研究的是三件事：低操作負擔的戰鬥循環、會改變陣容容量的建設里程碑，以及能解釋配隊效果的傷害統計。單純增加英雄和光效，未必能建立同樣的留存動機。（推論）

## 2. 遊戲循環與操作分工

官方定位是英雄與塔組合的放置守城，支援後台戰鬥，並提供技能、裝備與長期養成。[官方商店](https://store.steampowered.com/app/4740930/?l=tchinese)

本次可驗證的流程：

1. 點擊城堡上的空槽，開啟單位選擇面板。
2. 選擇火焰炮手，點「上陣」，角色出現在城堡上方。
3. 按「開始戰鬥」，進入獨立戰鬥 HUD，敵人由右向左逼近。
4. 英雄會自動攻擊；主炮教學要求玩家親自瞄準。
5. 戰鬥後回到建設版面，投入金幣提升城堡，解鎖更多可配置位置。

戰鬥版面有「結束戰鬥」「自動施法」「1X」及 1～0 技能快捷槽。這些控制項的存在已確認；倍速上限、自動戰鬥開放條件、技能耗魔規則尚未完整測試。

**設計解讀：**英雄負責穩定輸出，主炮提供親手參與的機會，養成提供長期回流理由。若你也做半放置遊戲，應讓手動操作有清楚收益，同時避免讓掛機玩家頻繁因操作缺席而完全無法推進。

## 3. UI layout

### 主戰場的空間分配

以下為本次 1080p 畫面的近似比例，不是原始 UI anchor：

| 區域 | 約略範圍 | 功能與分析 |
|---|---|---|
| 頂部狀態 | y=0～150，約 14% 高度 | 左 HP、右 MP、中央波次。三個主要狀態容易定位，但兩條大型裝飾框佔用不少空間。 |
| 場景展示 | y=150～850 | 大量天空留白；城堡與角色集中在下半部。利於展示高塔、飛行敵人，但開局視覺密度偏低。 |
| 地面作戰帶 | 約 y=740～850 | 地面敵人、命中效果、掉落回饋集中。密集怪潮時可能互相遮擋。 |
| 底部控制 | y=855～1080，約 21% 高度 | 常用操作常駐；戰前與戰鬥中切換內容。 |

戰前底欄：左側等級與資源、城堡升級、記錄／屬性；中央開始戰鬥；右側系統圖示。戰鬥底欄：左側資源與各單位傷害柱；中央結束戰鬥、自動施法、速度；右側兩排技能槽。（實測）

**值得借鑑：**相同空間隨狀態切換用途，不把所有功能同時攤開；開始／結束戰鬥維持在接近的位置；資源留在左下，玩家不必重新找。

**可改善：**初期大量鎖住或剪影圖示，資訊量高但可操作內容少；若不顯示解鎖條件，會增加試點成本。底部中央厚重龍形裝飾強化題材，但讓主按鈕比必要尺寸更佔空間。建議以「下個明確目標」取代多個未知鎖頭。

### 單位管理面板

採左右雙頁：左側詳情，右側列表。左側包含名稱、星級、大角色展示、六格屬性、技能、兩個裝備槽，以及升星／升級／上陣／攻擊方式。右側上方有英雄、防禦塔、主炮、隊長等分類與卡片列表；底部有編隊選擇和編隊按鈕。（實測）

這個模板可讓多種單位共用操作結構，降低學習成本。缺點是屬性多以圖示表達，首次閱讀時不能直接確認每個百分比意義。自己的遊戲建議提供圖示文字提示、目前值→升級後值、成本與預估輸出變化。列表能依元素、職能、攻擊目標及是否上陣篩選，比單純擴大卡片數量更實用。

### 新手引導

遮罩壓暗背景，以黃色箭頭指向當前目標，逐步要求選人、上陣、開戰、升城、配置弩車。（實測）

優點是第一輪流程不容易迷路。限制是連續要求升城四次，玩家容易只完成點擊而未理解投資原因。建議每次教學只傳達一個可驗證因果，例如「城堡 Lv.5 開主炮槽」，並在按鈕旁直接顯示進度。

## 4. 素質、數值與經濟

### 城堡實測表

| 城堡等級 | 最大 HP | 最大 MP | 畫面顯示的下一級金幣成本 |
|---|---:|---:|---:|
| 1 | 105 | 60 | 150 |
| 2 | 160 | 70 | 300 |
| 3 | 215 | 80 | 450 |
| 4 | 270 | 90 | 650 |
| 5 | 325 | 100 | 800 |

Lv.1→5 共花 1,550 金幣。這五個點符合 HP=105+55×(L−1)、MP=60+10×(L−1)，但只能描述此區間，不能外推到高等級。成本在第四次跳到 650，已不是固定加 150 的簡單序列。

開局畫面為 1,300 金幣、20 紫色資源、EXP 0；第一波後看到 1,750、21、450。這是教學流程的淨變化，不能直接宣稱所有一般關卡固定給 450 金幣與 1 紫色資源。升城後 EXP 450 保留，表示至少此處城堡升級沒有消耗顯示的 EXP。（實測）

### 單位初始值

| 單位 | 等級 | 劍圖示值 | 頻率 | 另見數值 |
|---|---:|---:|---:|---|
| 火焰炮手 | 1 | 6 | 2.3 次／秒 | 150%、0%、0%、100 |
| 破城弩車 | 1 | 12 | 1.5 次／秒 | 150%、0%、0%、90 |

未取得 tooltip 的欄位保留原始圖示／數字，不把 100、90 擅自解讀成射程或命中率。

只計攻擊與頻率的基準為 13.8 與 18／秒，但後續取得弩車普通技能 130% 物理傷害的 tooltip，因此含此係數的弩車名目基準應為 23.4／秒。這些都不是實測 DPS；攻擊動畫、彈道、範圍傷害、過量傷害、目標移動與手動瞄準都會改變結果。詳見完整研究報告與截圖 22。

### 應如何評估平衡

對你自己的同類型遊戲，應追蹤「投資後多打幾波／每分鐘多賺多少」，而非只比面板戰力。攻擊與攻速可能相乘，控制會延長敵人在射程內的時間，AOE 的價值隨怪物密度上升；這些因素都可能讓同等面板傷害產生不同收益。（分析建議）

建議資料表欄位：單位、等級、升級成本、單發傷害、攻擊間隔、目標數、範圍、投射物速度、技能係數、MP、冷卻、控制時間、波次、敵人 HP、敵人移速、漏怪數、通關秒數、每分鐘收益。先量測單因素，再測組合，避免把多次升級的效果混在一起。

戰鬥 HUD 標示「DPS總量傷害」並顯示各單位柱狀圖；文字混合 DPS 與總傷害概念，尚不能確定採樣窗。自己的遊戲應分開標示「累積傷害」與「近 10 秒 DPS」，並說明是否計入召喚物、持續傷害和過量傷害。

## 5. 美術、動畫、Shader 與渲染

### 能確認的事項

安裝目錄有 UnityPlayer.dll、UnityCrashHandler64.exe、GameAssembly.dll，資料目錄有 il2cpp_data：可辨識為 Unity 的 IL2CPP 建置。沒有據此確認 Unity 版本、Built-in／URP、2D Renderer、材質名稱或自訂 Shader 原始碼。

畫面可見：像素角色與城堡、分層的火山背景、厚邊框 UI；標題場景有多組地面和飛行角色；戰鬥有彈道、火焰命中、浮動傷害數字、金幣跳字；升級有金色粒子、直向光條、綠色 Lv+1；弩箭帶柔白拖尾；游標與瞄準標記有發光外觀。（實測）

這套視覺的層次主要來自「遠景低對比、前景輪廓、角色剪影、局部高亮」，不能把所有亮光都歸因於昂貴 Shader。

### 效果拆解與可行重建法

以下是達到相近效果的工程方案，**不是對方實際實作的宣稱**：

| 效果 | 可行實作 | 驗證／注意事項 |
|---|---|---|
| 像素角色 | Sprite atlas + 序列幀，Point filtering，固定像素比例 | 紋理細節清楚不代表一定用了 Pixel Perfect Camera；測移動時是否抖動。 |
| 火焰命中 | 序列幀火焰 sprite 疊加亮色核心，少量粒子 | 先確認動畫輪廓，再考慮 Bloom；光暈過強會吃掉像素細節。 |
| 弩箭拖尾 | 淡出貼圖、拉伸粒子或 Trail mesh | 單張截圖不能辨識使用哪一種。測大量箭矢透明 overdraw。 |
| 升級閃光 | 粒子、向上光條、浮動文字 | 不必為每個粒子實例化獨立材質。 |
| 受擊閃白 | Sprite shader 的顏色插值 | 本次尚未單獨確認閃白；作為自己遊戲的建議效果。 |
| 選中描邊 | 鄰近 alpha 採樣或預製外框 sprite | 卡片綠色選框可能只是 UI 圖，不能據此證明使用 outline shader。 |
| 教學遮罩 | 半透明全屏 UI + 高亮目標／遮罩洞 | 主要屬於 UI 合成問題，不需要全場後處理。 |
| 場景深度 | 多層背景、色彩與明度分離 | 靜態畫面不能證明一定有 parallax。 |

### 建議的渲染順序

遠景／天空 → 遠山／中景 → 地面 → 城堡及設施 → 單位 → 投射物與世界特效 → 世界文字／血條 → HUD → 模態遮罩與教學。

這是自己的實作建議。角色與特效應有清楚排序規則，避免箭矢被錯誤遮住、地面火焰蓋掉敵人剪影。像素世界和高解析 UI 可分開處理：世界控制採樣，UI 保持文字可讀性；不要把整個 UI 低解析縮放。

### 效能研究界線

畫面右上有 GPU／CPU overlay，但當時 FPS 為 N/A；不能用瞬間百分比判定本作效能好壞。也不能從建議顯卡要求反推出 Shader 複雜度。

自己的原型應以固定機器、解析度和怪物數做測試：100／300／1000 單位、不同投射物數、浮字開關、後處理開關，量測 frame time、draw calls、GC 和透明像素覆蓋。優先檢查尋敵、碰撞、物件生成、浮字與粒子，再決定是否需要更複雜的渲染技術。後台掛機尤其要測限幀、失焦後模擬、倍速、暫停和存檔，而非只看前景 FPS。

## 7. 對你的遊戲的落地優先序

**第一優先：做一個能驗證循環的切片。** 一座城、三種職能單位、數個明確差異的敵人、十波關卡；從配置→開戰→獲得收益→投資→戰場改變完整跑通。不要先用大量內容掩蓋沒有決策的循環。

**第二優先：讓玩家看懂為什麼變強。** 升級顯示前後值；戰後分清單體、AOE、控制和輔助貢獻；下一個槽位明示解鎖條件。差異化可以來自「資訊透明、換隊方便、試錯便宜」。

**第三優先：建立一致的視覺與回饋。** 先統一像素尺度、輪廓、配色、角色基準線、UI 字級與命中節奏，再加受擊、拖尾、粒子等效果。以可讀性和效能預算約束 Shader。

**第四優先：驗證中後期。** 檢查是否出現唯一最優解、純粹數值牆、重複點擊與無效掛機。以不同密度、飛行／地面、快速／高血量敵人測試陣容價值，而非只把每波 HP 調高。
