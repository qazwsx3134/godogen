# 遊戲開發流程（Flow）

從點子到上架，各階段要產出哪些文件、要通過什麼關卡、用哪個工具。整條流程最貴的錯誤只有一種：**玩法和技術還沒驗證，就投入正式美術與內容**。所以前期驗證放在最前面，每一階段都要過了關卡才往下走。

## 總覽

```
 ┌────────────┐   ┌──────────────────────┐   ┌──────────────┐
 │ 0 概念     │──→│ 1 前期驗證           │──→│ 關卡 1       │
 │ 一句話玩法 │   │ placeholder 原型     │   │ 繼續／轉向／ │
 │ 目標玩家   │   │ 技術試作（spike）    │   │ 放棄         │
 └────────────┘   └──────────────────────┘   └──────┬───────┘
       ↑                  ↑ 轉向                    │
       └──── 放棄 ────────┴─────────────────────────┤
  ┌───────────────────── 繼續 ──────────────────────┘
  ↓
 ┌──────────────────────┐   ┌──────────────┐   ┌──────────────┐
 │ 2 設計文件           │──→│ 關卡 2       │──→│ 3 製作       │
 │ GDD／策劃／TDD       │   │ 文件夠不夠做 │   │ 依里程碑迭代 │
 │ 資源與時程           │   └──────────────┘   └──────┬───────┘
 └──────────────────────┘                           │
                                                    ↓
 ┌──────────────┐   ┌──────────────────────┐   ┌──────────────┐
 │ 6 上架       │←──│ 5 QA                 │←──│ 4 評審       │
 │ itch.io 等   │   │ 阻斷／打通／兼容／   │   │ 好不好玩     │
 │              │   │ 回歸                 │   │ 開發健檢     │
 └──────────────┘   └──────────────────────┘   └──────────────┘
                     4、5 沒過 → 回到 3 修改
```

| 階段 | 產出 | 過關條件 | 工具 |
|---|---|---|---|
| 0 概念 | 一句話玩法、目標玩家、參考遊戲 | 講得出「玩家每分鐘在做什麼」 | Studio `brainstorm` |
| 1 前期驗證 | 原型＋README（假設、通過條件、結論） | 玩法假設通過；最難 3 個技術點都量到數字 | Studio `prototype`、godot-kit |
| 2 設計文件 | GDD、策劃細節、TDD、資源與時程 | 下一個里程碑需要的項目都「有」且夠具體 | `design-system`、`create-architecture`、`sprint-plan` |
| 3 製作 | 可玩版本、`PROGRESS.md` | 里程碑驗收條件達成 | `dev-story`、godot-kit 模組 |
| 4 評審 | `reviews/YYYY-MM-DD-game-critic.md` | 沒有未處理的高影響問題 | skill `game-critic` |
| 5 QA | 測試結果、兼容性紀錄 | 沒有阻斷性缺陷；流程打通 | `qa-plan`、`smoke-check`、`regression-suite`、`gate-check` |
| 6 上架 | 匯出版、商店頁 | 匯出版在目標平台實測可玩 | skill `godot-prototype-to-itch`、`itch-publish`、`release-checklist` |

## 1. 前期驗證：玩法與技術可行性

玩法驗證和技術驗證同時進行，兩條都通過才進到關卡 1。

```
                ┌─→ 玩法原型 ──────────────────────────┐
                │   色塊、合成音、假文字，幾天內可玩   │
 一句話玩法 ────┤   通過條件可判定，例如：             ├─→ 關卡 1
                │   「不操作會輸、高手會贏、           │
                │    試玩五次願意繼續」                │
                │                                      │
                └─→ 技術試作 ──────────────────────────┘
                    最難的 3 點，各量出一個數字：
                    效能（幀時間、draw call）、網頁版大小、
                    觸控與 Safe Area、存檔
```

- **原型 README** 必寫：要驗證的假設、怎麼執行、狀態、結論（見 `.claude/rules/prototype-code.md`）。
- **placeholder 優先**：用 godot-kit 的 `synth.gd` 當暫時音效，美術用色塊。正式美術要等關卡 1 通過。
- **關卡 1 的結論**寫進 README：繼續、轉向（改假設後回到原型）或放棄（回到概念）。

## 2. 設計文件

```
 設計文件
 ├─ GDD（遊戲設計）
 │   ├─ 核心玩法 ── loop 圖：秒／分鐘／小時天三層
 │   ├─ 美術 ───── 風格參考、art bible、素材清單（含數量）
 │   ├─ 音效 ───── 音效清單、音樂情境
 │   └─ 劇情 ───── 主線大綱、角色、怎麼接進玩法
 ├─ 策劃細節
 │   ├─ 角色能力 ── 數值表
 │   ├─ 戰鬥機制 ── 傷害公式、命中、冷卻、勝負條件
 │   ├─ 技能數 ──── 確定的數字與清單，各有用途
 │   ├─ AI 邏輯 ─── 每種敵人的狀態或優先順序，玩家能反制
 │   └─ 關卡構建 ── 關卡數、每關教什麼、難度曲線
 ├─ TDD（技術設計）
 │   └─ 引擎與版本、目標平台、效能預算、存檔格式、第三方套件
 └─ 資源與時程
     └─ 素材與功能的工作量、里程碑日期與驗收條件
```

- **夠具體的標準**：寫數字和清單，不寫形容詞。例如「技能 8 個」，不寫「技能很多」。
- **原型階段不必全部寫完**。只補下一個里程碑需要的項目，其餘寫「待定」。
- 文件和程式不一致時，以程式為準並更新文件。`game-critic` 會把這種情況標成「過時」。

## 3. 製作：每個里程碑的循環

```
 ┌─→ 規劃（sprint-plan）─→ 實作 ─→ 測試（L1／L2）─→ 紀錄 ─┐
 │                                                        │
 └──────── 下一個里程碑 ←── 使用者手動驗收 ←── L3 ←───────┘
```

- **紀錄**：每次 commit 前更新該原型的 `PROGRESS.md`，舊段落移到 `MILESTONE.md`，再更新根目錄的 `Progress.md`（見 `AGENTS.md`「進度紀錄與交接」）。
- **畫面用 scene 組成**，不在程式裡用 `.new()` 建整個畫面（見 `AGENTS.md`「Godot 開發」）。
- **遇到不合理的失敗**先查 `LESSONS.md`。

## 4. 評審

skill `game-critic` 一次看兩部分：

```
 A 玩家體驗（好不好玩）           B 開發健檢（做得對不對）
 ├─ 1 心流：challenge／skill      ├─ 6 前期驗證做了沒
 ├─ 2 隨機：上癮還是挫折          ├─ 7 文件：有／缺／過時
 ├─ 3 Loop：短、中、長期          └─ 8 QA 擋不擋得住壞版本
 ├─ 4 每個行動都有回饋
 └─ 5 八角框架
                 ↓
   建議依「影響 × 成本」排序，每條附「改完怎麼驗證」
```

越早期越要看 B。玩法驗證之前，A 的分數只能參考。

## 5. QA

```
 每次改動              里程碑結束（使用者驗收後）    上架前
 ┌──────────────┐     ┌────────────────────┐       ┌──────────────┐
 │ L1 單元測試  │     │ L3 完整測試        │       │ 兼容性實測   │
 │ L2 ＋冒煙    │──→  │ 流程打通           │──→    │ 各目標平台   │
 │   （回歸）   │     │ 阻斷性缺陷清零     │       │ 匯出版       │
 └──────────────┘     └────────────────────┘       └──────────────┘
```

| 項目 | 檢查什麼 | 不通過時 |
|---|---|---|
| 阻斷性缺陷 | 當機、卡死、存檔遺失、無法開始或結束一局 | 有一個沒修就不能發布 |
| 流程打通 | 啟動 → 教學 → 核心 loop → 結算或存檔 → 重開讀檔，有一條自動測試或 bot 跑完整條 | 補端到端測試 |
| 兼容性 | 目標平台、螢幕比例、Safe Area、觸控與滑鼠；匯出版和編輯器分開測 | 沒測過的平台標「未測」 |
| 回歸 | 每個修過的 bug 有對應測試；README 寫明 L1／L2／L3 各跑哪些指令 | 用 `regression-suite` 補 |

- 測試分層的完整規則見 `AGENTS.md`「KISS 與分層測試驗收」：只跑足以證明這次改動的那一層。
- 音效同步、手感和實機效能，headless 環境無法證明，要在實機確認。

## 6. 上架

照 skill `godot-prototype-to-itch` 的步驟：網頁匯出、縮小檔案、用真瀏覽器驗證、上傳 itch.io。上架前跑一次 `release-checklist`。

## 文件放哪裡

| 文件 | 位置 |
|---|---|
| 原型 README（假設、結論） | `prototypes/<原型>/README.md` |
| GDD、策劃、TDD | `prototypes/<原型>/design/`，或專案自己的 `docs/` |
| 進度與交接 | `prototypes/<原型>/PROGRESS.md`、`MILESTONE.md`，根目錄 `Progress.md` |
| 評審報告 | `prototypes/<原型>/reviews/` |
| 踩過的坑 | `prototypes/LESSONS.md` |
| 測試指令 | 該原型的 README 或 AGENTS.md |
