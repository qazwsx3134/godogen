# 聖地展望台 — 專案文件

手機第一人稱的動畫聖地展望台。玩家站在一座固定的觀景平台上，平台內可以小範圍走動，也能環顧、拉近看，欣賞經典場景。第一個景點是《火影忍者》的火影岩。

本檔是決策版：方向、規格數字和裁定以這裡為準。可執行清單在 [TODO.md](TODO.md)，操作方式與 v0 實測數字在 [README.md](README.md)。

狀態（2026-10-01）：v0 能跑，但美術不合格。使用者評語是岩壁與村莊建築「非常醜」，因此改走「AI 生成高模 → 減面烘焙」路線（B 路線），先用一顆頭做 spike 驗證。

## 設計支柱

1. **像到那裡**：寫實質感，地標一眼就認得出來。辨識度優先於細節量。
2. **視點固定，所以花得少**：平台是 8.4 × 6.2 m 的矩形，離岩壁約 170 m，玩家走動造成的視差不到 3°。看不到的地方不做；越遠，用的三角形和貼圖越少。
3. **手機跑得動**：GL Compatibility、中階手機。效能預算是驗收條件，不是參考值。
4. **景點可替換**：觀看器（Viewer／HUD／品質檔位）與景點 scene 分開。下一個景點只換資料和資產，不改觀看器。

## 已有的東西（v0）

```
 main.tscn ─┬─ Spot: hokage_rock.tscn（天空、太陽、霧、岩壁、地面、村落、火影大樓、平台）
            │     └─ Viewer（第一人稱：走動範圍、視角錐、FOV 都有上下限）
            └─ HUD（搖桿、環顧觸控面、望遠鏡、回正、介紹卡）
```

- 互動測試 21 項全過（`tests/test_viewer.gd`）；截圖與效能預算檢查在 `tests/capture.gd`。
- 岩壁與臉是程序生成：Python 的高度場轉成網格加法線貼圖。村莊是方盒子 MultiMesh。**這兩者都會被取代**，程序化的臉只保留作為新資產進來前的佔位。
- 會沿用的部分：觀看器、HUD、品質檔位、地面與道路的 `layout.json`、崖體高度場（只把臉換掉）、截圖與預算框架。

| D2 | 建模走 **B 路線**：AI 圖轉 3D 生成高模，再由我們自己減面和烘焙 | 使用者選定。程序 SDF 雕出來的臉不夠好看，手工雕刻又太吃時間 | 10-01 |
| D3 | 3D 由**使用者自己用 Meshy 或 Tripo 生成**；Claude 提供輸入圖規格與匯出設定，接手後續處理 | 使用者決定。兩家都可以用，spike 時同一張圖兩家各做一次來比較 | 10-01 |
| D4 | 生成時**不設面數上限**，也不用平台內建的 remesh；減面由我們依「展望台看得到什麼」來做 | 平台的 face_limit 是整顆平均減面，不知道玩家的視點。我們的優勢是視點已知 | 10-01 |
| D5 | 火影岩**拆成 4 顆頭各自生成**，崖體繼續用程序高度場 | 圖轉 3D 的解析度是「每個物件」給的，拆開等於每張臉都吃滿解析度。4 顆頭要從同一張定稿圖裁切，風格才會一致 | 10-01 |
| D6 | Blender 以 **headless Python 腳本**為主（`blender -b -P`，腳本放 `tools/blender/`）。Blender MCP 只當輔助，用來互動檢查和手修 | 腳本能重跑、能 diff，符合「產生器是製作工具」的規則。MCP 的操作沒辦法重現 | 10-01 |
| D7 | 光照以**白天**為主。太陽和天空保持動態；只烘焙不受光線方向影響的 AO，albedo 要去除光影 | 保留以後切換時段的可能（使用者說「可以考慮」）。如果把光影烘進貼圖，就只能是白天 | 10-01 |
| D8 | 岩石的大面積材質用 **CC0 實拍 PBR 貼圖**（ambientCG／Poly Haven），每組記錄來源、版本與授權 | 寫實需要實拍質感，程序雜訊做不出來；CC0 沒有授權疑慮 | 10-01 |
| D9 | 驗收用**像素誤差**，不用面數：從平台取樣點看過去，高低模的輪廓差距要在門檻內 | 面數只是結果，玩家看到的是像素 | 10-01 |
| D10 | 岩壁只做**單一 LOD**；距離 LOD 用在村莊 | 岩壁上每一點離平台都約 170–200 m，距離差不多。決定面數的是望遠鏡（24°）。村莊從 30 m 到 600 m 都有，才是距離 LOD 的主場 | 10-01 |

## B 路線：火影岩完整流程

每顆頭都走同一條流程。第一次用四代（湊）做 spike，通過後其他三顆照做。

```
 階段 0  前置（只做一次）
   [你] 安裝 Blender
   [我] 修 v0 貼圖匯入設定（VRAM 壓縮、mipmap、法線貼圖旗標），重新截圖作為新基準
   [我] 寫 tools/blender/ 管線，先拿 v0 的程序化臉當假高模跑通全程
        └ 不必等 AI 模型；之後真模型一到就能直接處理
          │
 階段 1  定稿圖
   [你] 生成整面岩壁、四顆頭的定稿圖（也可以請我用 Gemini 生，約 10¢）
   ◆ 關卡 A [你]：四張臉都認得出來、風格一致、是寫實的花崗岩
          │ 不通過 → 改 prompt 重新生成
 階段 2  輸入圖
   [你] 從定稿圖裁出單顆頭，用 img2img 整理成符合規格的輸入圖（加一張側面圖更好）
          │
 階段 3  生成高模
   [你] 同一張輸入圖在 Meshy 和 Tripo 各生成一次，放進 art_src/…/<name>/{meshy,tripo}/
        附 notes.md（設定、費用、日期）
          │
 階段 4  Blender 管線 [我]（headless，每一步都可單獨重跑；兩家的模型各跑一次）
   1 normalize  統一單位（公尺）、朝向（+Z 面向村子）、擺到崖面座標
   2 cull       從平台取樣點做射線可見性測試，刪掉看不到的面（背面、底部、深凹處）
   3 decimate   Decimate collapse 加頂點權重：剪影邊保留幾何，正面內部的細節交給法線貼圖
   4 uv         從平台中心做透視投影，貼圖解析度照玩家看到的螢幕面積分配
   5 bake       Cycles selected-to-active，用 cage：
                albedo（去光影）、法線（OpenGL Y+）、AO → ORM
   6 export     head_<name>.glb ＋ 1K 貼圖
   7 report     從平台 3 點 × 2 種 FOV 渲染高低模對照圖，輸出像素誤差與面數 JSON
   ◆ 關卡 B [我]：面數 ≤ 15k；輪廓誤差 55° 時 ≤ 1 px、24° 時 ≤ 2 px
          │ 不通過 → 先調減面權重；還是不行，再放寬面數（上調要寫進本檔）
 階段 5  進 Godot [我]
   匯入（VRAM 壓縮、mipmap、法線貼圖旗標）→ 嵌進崖體（拿掉那顆頭的程序浮雕）
   → capture.gd 截 high、mid、low 三個檔位 → 檢查整幀效能預算
   ◆ 關卡 C [我]：效能預算 OK；互動測試全過
          │
 階段 6  審核 [你]
   看平台視角、望遠鏡、Meshy 與 Tripo 並排比較的截圖
   ◆ 關卡 D [你]：辨識度和寫實度過關，並選定 Meshy 或 Tripo
          │ 不通過 → 依問題回到階段 1、2 或 3
 階段 7  收尾 [我]
   結果與預算校正寫進本檔和 TODO
   commit 只加入 prototypes/seichi-pov/ 和 prototypes/README.md
   （工作區裡其他未完成的變更不屬於本原型，不要夾帶）
```

**重試規則**：同一個關卡最多連續失敗兩輪。第三輪開始前必須換一件事：換生成平台、換輸入圖的做法，或回頭找使用者討論。不能只是用同樣的做法再跑一次。

### 輸入圖規格（給使用者生成用）

- **視角**：從正面**略往上看**（仰角約 15°）。平台的眼睛高度約 27 m，臉的中心約 78 m，距離約 170 m，實際看過去就是仰視。不要用一般物件常見的俯視 3/4 角度。
- **內容**：單一顆頭的岩雕，周圍帶一點岩體，寫實的花崗岩質感，臉要可辨識（四代：刺蝟髮、長側髮）。
- **光線**：陰天平光，不要強烈陰影和高光。背景是純灰色、不透明，**不要去背**。
- **一致性**：先生成一張「整面岩壁、四顆頭」的定稿圖，再從同一張圖裁出各顆頭，用 img2img 整理成單顆的輸入圖。如果平台支援多視角輸入（兩家都支援），加一張側面圖，讓突出深度比較準。

### 生成與交付設定

| 項目 | 設定 |
|---|---|
| 幾何 | 最高品質，不設 face limit，關閉 remesh／quad，三角面 |
| 貼圖 | PBR 開，最高解析度 |
| 格式 | GLB |
| 放哪裡 | `art_src/hokage_rock/heads/<name>/`：`input.png`、`raw.glb`、`notes.md`（哪家、什麼設定、多少錢、生成日期） |

`art_src/` 是原始素材，不被遊戲載入；只有管線產出的低模與貼圖才進 `spots/hokage_rock/`。

## 規格與預算（暫定，spike 後校正）

依據：720p、FOV 55° 時，170 m 外 1 px 約 0.25 m；望遠鏡 24° 時約 0.10 m。

| 項目 | 數字 | 依據／備註 |
|---|---|---|
| 每顆頭的三角形 | ≤ 15k（4 顆合計 ≤ 60k） | v0 整片崖面 64k；臉換成 AI 模型後，總量不應增加 |
| 輪廓誤差 | 55° 時 ≤ 1 px；24° 時 ≤ 2 px | 從平台 3 個取樣點量 |
| 每顆頭的貼圖 | albedo、法線、ORM 各 1K（用 2K 烘焙再縮小） | 一顆頭約 45 m 寬，1K 等於每 texel 4.4 cm；望遠鏡下 1 px 約 10 cm，仍有 2 倍餘裕 |
| 岩壁貼圖 VRAM | ≤ 32 MB（ASTC，含 mipmap） | 4 顆頭約 16 MB，再加崖體貼圖 |
| 整幀三角形／draw call | ≤ 250k／100（含陰影 pass） | **暫定**：v0 實測 207k 之後才訂的，還沒上實機驗證 |
| 品質檔位 | high、mid、low 都要截圖 | 手機實際只會拿到 mid 或 low |

## 之後：村莊（等岩壁驗證完才開工）

- 一樣讓使用者用 Meshy／Tripo 生成，但房屋是小物件，**可以直接設 face limit 2–5k、不烘焙**。先做 8–12 種木葉房型，加上火影大樓這個主角資產。
- 依距離分層：近景（< 100 m）用完整模型；中景（100–400 m）用 Godot 匯入時自動產生的 LOD 加 `visibility_range`；遠景（> 400 m）用背景板。
- 要有木葉的辨識元素：圓筒水塔、紅色屋頂、電線桿、晾衣繩、店家布簾。這些比面數重要。
