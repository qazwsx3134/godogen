# 系統文件契約與交付標準

2026-10-26；狀態：規劃草案。此文件回答「每個系統要寫什麼文件、寫到什麼程度才能開工」。[系統工作包](../../design/gdd/systems-index.md)定義各系統專屬內容，本頁定義共通完成標準。

## 文件層次與使用順序

```text
研究證據＋手機基準 → game brief／系統索引
                              ↓
                     各系統 planning dossier
                              ↓
            GDD ↔ UX／數值資料 ↔ Godot TDD／ADR
                              ↓
                    story／實作／scene／資料
                              ↓
               QA 案例 → 自動／手動／真機證據
```

GDD 定義玩家規則，TDD 定義程式責任，UX 定義操作與資訊呈現，資料表是可調整內容，QA 驗證實際行為。它們互相引用同一規則 ID，避免各自保存不同數值。

本次已完成的是 planning dossiers、系統索引、roadmap 與共通架構草案。**不是 40 份已定案的完整 GDD，也不是 40 個已完成的功能。** 依里程碑逐一補齊本階段必要細節，不為後期條件功能先填大量虛構數值。

## 每系統文件矩陣

| 文件 | 何時需要 | 必須回答 | 完成條件 |
|---|---|---|---|
| Planning dossier | 所有系統，本次各一份 | 為何做、做什麼、依賴誰、文件與工作包 | 有明確責任、初始前置、階段範圍、至少 3 條 AC |
| GDD／規則規格 | 每個要實作的玩法；純基礎系統可用行為契約 | 玩家能做什麼、規則與失敗結果 | 每個狀態有進出條件，例外處理有結果，未定值已標示 |
| 數值與資料規格 | 定義速率／機率／成本／曲線／門檻的系統 | 變數、單位、資料源、上下限、算例 | 有樣本、驗證規則、調整影響，來源與試調值分開 |
| Godot TDD | 有新模組或重要介面變更 | scene tree、所有權、命令／事件、更新與保存時機 | 實作者不用猜哪裡算傷害／扣料／存檔；有遷移與測試路徑 |
| UX spec | 玩家可操作或需要讀資訊的系統 | 流程、焦點、觸控、安全區、錯誤／loading／空狀態 | 主要動作可純觸控完成，狀態與錯誤可辨識 |
| 資產／動畫／音效表 | 有新視覺／聲音內容 | ID、尺寸／方向／幀、錨點、事件時間線、來源 | 可對照 manifest，自動驗缺檔，原創／授權與生成狀態明確 |
| QA spec | 每個交付系統 | 哪個規則要用何種證據驗證 | AC→案例→結果／證據可追蹤，未驗證不寫 PASS |
| ADR | 影響多系統或返工成本大的選擇 | 背景、選項、決定、影響與失效條件 | 決定狀態清楚；草案不寫 Accepted |
| story／實作交接 | 開工時 | 這次做哪段、改哪些檔、依哪些契約、如何驗收 | 範圍可單獨審查，依賴可用，沒有隱藏設計問題 |
| 維護／營運 runbook | 保存、建置、後端、付款等需操作的系統 | 如何建立／恢復／升級／回滾／查錯 | 由乾淨環境與測試資料能重跑，敏感操作有權限與證據 |

不適用的附件標 N/A 並附原因。例如內容登錄可借用開發工具輸出作 UX，不必創造玩家面板。共用窗口 shell 不在每份 UX 重複定義樣式；每個系統只補自己的內容、狀態與動作。

## GDD 必寫內容

正式玩法規格可沿 Studio 八節結構撰寫：

1. **Overview**：系統目標、範圍、本階段交付與後期擴充。
2. **Player Fantasy**：玩家感受到的價值，例如換武器的進步、寵物的陪伴；純技術系統描述服務的玩家體驗。
3. **Detailed Rules**：逐步正常流程、狀態機、輸入、拒絕原因、資源增減與權威端。不能只寫「正確處理」。
4. **Formulas**：變數、單位、取整、順序、上下限與至少一個算例；無數值規則時說明 N/A。
5. **Edge Cases**：取消、死亡、滿包、無目標、切區、背景、斷線、舊資料與重送的具體結果。
6. **Dependencies**：上游輸入、下游輸出、誰有權修改狀態；對應雙向連結。
7. **Tuning Knobs**：可調參數、安全範圍與對玩法／手機成本的影響；試調值標明非原作資料。
8. **Acceptance Criteria**：能測出的通過／失敗條件，沿用 `AC-Sxx-nn` 並細分。

例如精煉不能只寫「失敗會退級」：必須寫哪個目標階、退到哪階、寶石／金幣／保護道具各消耗多少、是否允許物品消失、重送怎麼回同結果。若這些尚未決定，該階段不能稱 Ready。

## Godot TDD 必寫內容

- **責任與樹**：主要 scene、item scene、Resource、行為腳本、唯一名稱節點；靜態版面能在編輯器看見。
- **狀態所有權**：Definition 只讀；RuntimeState 屬權威服務；UI 是 view model；event 只描述已發生的結果。
- **契約**：命令參數、回傳錯誤碼、事件欄位、版本、idempotency、取消／失效策略。
- **更新時機**：physics tick／動畫／clock／背景；哪些可降頻，哪些必須保持權威一致。
- **資料生命週期**：載入、共用、深拷貝時機、卸載、切區清理、保存片段與 migration。
- **整合遷移**：現有 `scripts/player.gd` 等哪段移出、哪段沿用；不要求一次重寫全部原型。
- **平台與 renderer**：Godot 4.7；Compatibility 基線；所用 shader／粒子／套件在實際目標匯出是否可用。
- **驗證**：domain 邊界、scene 實例化、輸入與真機情境；效能報告記裝置與負載。

主要程式命名在 dossier 只是建議，正式 API 由 TDD 統一。重大選擇先記 ADR 提案，不以規劃文中的函式名冒充既有 Godot API 或既有專案功能。

## UX、資料與 QA 的範例

### 背包／換裝

GDD 定義堆疊、容量、裝備欄與限制；資料表有 ItemDefinition 與 ItemInstance；TDD 指定 InventoryTransaction 與 AppearanceResolver；UX 提供選物→比較→裝備、滿包與取消狀態；QA 測滿包交換、重送與同 uuid 守恆。

### 觸控／相機

UX 記錄單指點地、多指按技能、開窗阻擋與 safe area；TDD 記錄 pointer capture 與固定 camera；場景文件列可調 node/export；真機證據驗證兩 aspect、背景返回與無旋轉需求。單靠 headless 不能判定可讀或不誤觸。

### 寵物／精煉

數值表明列測試規則與未知來源；UX 顯示投入與失敗後果；TDD 說明時間／RNG／transaction；QA 重送不再抽、背景不亂扣／加、存讀不重複產出。後期接多人後另測服務端資料耐久性。

## 文件與功能狀態

| 狀態 | 表示 | 不表示 |
|---|---|---|
| Planning Draft | 責任、文件與工作包已列出 | 詳細公式／平台已定 |
| Spec Draft | 本階段規則、UX、TDD 已寫 | 已通過設計審查 |
| Ready for Implementation | 前置契約、資料樣本、AC、決策均足夠 | 使用者已授權發佈或付款 |
| In Progress | 正在改程式／scene／資料 | 任何 AC 已通過 |
| Implemented, Unverified | 改動完成等待證據 | 真機／完整循環完成 |
| Verified | 本階段 AC 有實際證據 | 後續擴充或所有平台都完成 |

本案 Studio 解析為 minimal／solo；使用者明確要求詳細文件，因此本次加深規劃，不改全域 rigor，也不觸發額外代理審查。只審查了文件一致性，未跑完整設計 gate。

## 從文件到開工的出口條件

前置規格可用 → 本階段所有產品決策明列 → 有可編輯場景／資料樣本計畫 → 有命令與所有權契約 → AC 可測 → story 明列 owner 檔案 → 開工。

只要是尚未決定的平台、付費或多人容量，保留在決策清單，先做不依賴該決策的工作。本次不開空白 GDD／TDD 冒充進度，也不把文檔檔數當成遊戲完成度。
