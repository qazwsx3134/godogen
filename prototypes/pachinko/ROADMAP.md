# 軌道連珠 Pachinko — Roadmap

2026-09-17：規格定案，尚未開工。規格見 [README.md](README.md)，詞彙見 [CONTEXT.md](CONTEXT.md)。

目前進度：**P0 未開始。**

## 要驗證的假設

> 純抽象的幾何演出，能不能撐起柏青哥的期待感。

這是一個試作，成功的定義是**回答這個問題**，不是產出可維護的程式碼。假設被推翻也是成功——那會省掉一整個專案。

判定方式是[前傾測試](README.md#驗收)：以設計值連續遊玩，黑洞接管出現時玩家會不自覺前傾或屏息。只有人能判，模擬腳本判不了。

執行順序是 **先讓數字對，再讓它好看，最後才讓別人拿得到**。理由是三個階段的失敗成本遞減：數字錯了，後面調演出調的全是假的；演出對了，交付只是工程問題。

## P0 骨架與數字（無美術）

讓整台機器在數學上成立。畫面上全部是純色塊，難看是預期的。

- Godot 4.7 專案、直式 9:16、2:3 機台置中、上下 HUD 帶
- 盤面物理：`RigidBody2D` 的球、固定釘子陣列、始動口、大入賞口
- 發射：按住連發、左打／右打兩檔
- 抽選（落入始動口即定案）、保留上限 4、持ち玉 收支、始動口賞球 3 顆
- 大當、確變ループ（突入率 65%）、出玉振り分け（10R／5R）
- 釘調整：每場開始時隨機微調釘子位置
- 演出佔位：三個色塊代表天體，對齊／不對齊，無動畫
- 模擬腳本 `sim.gd`（`godot --headless --script`）

**出場條件**：模擬腳本全綠——

| 檢查項 | 目標 |
| --- | --- |
| 大當機率 | ≈ 1/319（開發旋鈕下 ≈ 1/99） |
| 確變継續率 | ≈ 65% |
| 平均出玉／大當 | 確變 ≈ 450 發、通常 ≈ 250 發 |
| 始動口入賞率（標準台） | 每 12 發一轉 |
| 始動口入賞率（釘調整分布） | 甘 ≈ 10、辛 ≈ 16，無離群 |
| 單場持ち玉 分布 | 有合理的輸／爆兩端，不是常數 |

釘子基準配置由實作時定，用 `sim.gd` 量出的始動口入賞率反覆校準到每 12 發一轉。這是 P0 最花時間的一步，而且**沒有捷徑**——它是全機唯一無法用數學推導的數字。

## P1 演出（軌道連珠）

把已經正確的數字變成有期待感的東西。這是整個試作真正要驗的部分。

- 軌道連珠的視覺語彙：三天體、軌道、連線判定（shader + particle，零生成美術）
- 四層接上抽選結果：數字轉動 → ノーマルリーチ（每 8 轉 / ≈0.008%）→ 黑洞接管（每 80 轉 / 25%）→ 三星連珠。信頼度加總必須回到 1/319，SP 吃掉幾乎全部預算，所以**中獎一律升級到 SP**
- 黑洞接管越出液晶邊界接管全螢幕；其他層留在液晶框內
- 音效：6 個 CC0 素材（球落盤、天體停止、リーチ、SP、大當、確變 BGM）
- 混音：靜默原則——通常時只有機械聲，SP 高潮前抽掉半秒再爆
- 回轉率按鈕（平時不顯示）

**出場條件**：前傾測試通過。固定標準台、1/319、3000 顆，連續玩完一場，黑洞接管出現時會不自覺前傾或屏息。

開發期用 1/99 + 1000 顆迭代（SP 每 25 轉一次，十分鐘看得到三次），驗收時才切設計值。

**這一階段有真正的失敗可能**：抽象幾何可能就是撐不起期待感。真的撐不起來，結論就是「需要角色」，而 [ADR 0003](docs/adr/0003-no-generated-art.md) 的價值正是讓這個結論乾淨——失敗不會是美術品質的問題，因為根本沒有美術品質這個變因。

## P2 交付

讓別人在自己的手機上點連結就能玩。

- 下載 Godot Web 匯出模板
- 決定 thread support 開關：開＝要 COOP/COEP header（itch.io 有設定），關＝不用 header 但效能較差
- iPhone Safari 實測：幀數（尤其黑洞接管）、觸控、音訊 gesture 解鎖
- 效能不足時把效果做便宜——**沒有原生退路**（[ADR 0004](docs/adr/0004-web-only-delivery.md)）
- itch.io 上架（`butler push`，`itch-publish` skill）

**出場條件**：把連結傳給一個沒看過這台機器的人，他用手機打開就能玩完一場，不需要任何說明。

> `.claude/rules/prototype-code.md` 寫「Prototypes must not be deployed or shipped」。這裡是**刻意偏離**：目標裝置是 iPhone，開發在 Linux/WSL，上架 itch.io 是唯一能讓球跑在目標裝置上的方法（[ADR 0004](docs/adr/0004-web-only-delivery.md)）。上架是為了測，不是為了發行——頁面保持 Draft 或不公開列出。

## P3 之後

**前傾測試通過才談**，沒通過就不該有 P3。而且這些是**升級成正式專案之後**的題目，**不在這個試作上實作**——照 `prototype-code.md`，試作驗證成功後是重寫，不是在原目錄上長。

- 台選び：開場給幾台，試打 100 發看回轉率再決定坐哪台
- 通常大當之後的時短
- 保留變化（保留球變色預告）
- SPSPリーチ、復活演出
- 角色演出（抽象版驗證成功後的加法，不是補救）
- 店內換台、跨台持ち玉

## 已知風險

| 風險 | 影響 | 現在的對策 |
| --- | --- | --- |
| 抽象演出撐不起期待感 | P1 失敗，整個試作的假設被推翻 | 這正是要驗的事。失敗有價值，因為它省掉一個完整專案 |
| iPhone Safari 上 shader 撐不住 | 交付不了 | 沒有原生退路，效能是設計約束；效果一開始就往便宜做 |
| 釘微調肉眼看不出來，玩家感覺不到「不同機台」 | P0 的釘調整白做 | 已知代價（真機也是如此）。回轉率按鈕是它唯一的可讀出口 |
| 始動口入賞率校準不到目標值 | P0 卡住 | 釘子配置是自由參數，可以一直調；`sim.gd` 是唯一的回饋管道 |
| 試作長大成正式專案 | 拋棄式的前提失效 | 先讓它拋棄式。前傾測試通過再談要不要升級 |
