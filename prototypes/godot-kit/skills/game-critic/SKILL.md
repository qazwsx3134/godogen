# 遊戲評審

這份 skill 不重講理論，只規定兩件事：每個判斷要拿什麼證據，報告要長什麼樣子。評審的重點是**證據**，不是一般性的設計常識。主 session 自己執行，不另外派 agent。

- **A 玩家體驗**（第 1–5 節）：好不好玩。
- **B 開發健檢**（第 6–8 節）：玩法和技術在前期驗證了沒、文件夠不夠做、QA 能不能擋住壞版本。

遊戲越早期，B 越重要：玩法還沒驗證就做正式美術，是最貴的錯。使用者只要其中一部分時，只做那部分。

## 和 Studio 的分工

這份 skill 只做 Studio 沒有的事：**對著可玩的版本**，用程式數值和短跑結果評分，並且算隨機的機率、套八角框架。理論標準沿用 Studio 的角色定義，不另訂一套；要深入時，交給下表的工作流程。

| 面向 | 沿用的標準 | 要深入時用 |
|---|---|---|
| 1 心流、3 loop、4 回饋 | `game-designer` 角色的 Flow、巢狀 loop、回饋時限 | `review-all-gdds`（loop 互相搶主線、經濟正回饋） |
| 2 隨機 | `economy-designer` 的保底；`live-ops-designer` 的掠奪式付費標記 | `balance-check` |
| 6 前期驗證 | `prototype` 的繼續／轉向／放棄結論 | `gate-check` |
| 7 設計文件 | — | `design-review`（單份 GDD）、`review-all-gdds`（跨 GDD） |
| 8 QA | — | `qa-plan`、`smoke-check`、`regression-suite` |
| 真人試玩紀錄 | — | `playtest-report` 整理後，當作 `[measured]` 證據 |

第 6–8 節只做**快速盤點**：有沒有、和程式一不一致。逐段審查交給上表的工作流程，不在這裡重做。

## 流程

```
蒐集證據 ─→ 列出動詞與 loop ─→ A：五個面向 ─┐
(文件／程式／短跑)               B：三個面向 ─┴→ 打分 ─→ 依「影響×成本」排序建議 ─→ 寫報告
```

1. **蒐集證據**，依可信度由高到低：
   - 程式與資料檔裡的真實數值：機率、HP、冷卻、獎勵表。
   - 短跑量測：專案 README 裡的 bot／平衡指令，每種只跑**幾局短的**，不跑長時間 soak；或看截圖。
   - 設計文件，例如 README、GDD、PROGRESS。

   找不到的就寫「未量測」，**不要編數字**。
2. **列出玩家動詞**：從 input handler、按鈕 signal、點擊事件找出玩家能做的每個動作。再列出各層 loop 的入口與出口。
3. **逐一評五個面向**（見下）。
4. **每個面向打 0–10 分**。每條發現都要標來源：`[code]`、`[measured]`、`[doc]` 或 `[inferred]`（推測）。只有 `[inferred]` 撐著的結論，要寫明「需實測」。

## 1. 心流：challenge 與 skill 是否平衡

- **三種玩家的結果**：不操作、普通、高手（可以用 bot 模擬）各自的勝率或存活時間。健康的樣子是「不操作會輸、普通勉強過、高手明顯贏」。三者差不多，代表選擇沒有意義，玩家會無聊；連高手都輸，玩家會焦慮。
- **難度曲線**：第一次失敗出現在第幾秒或第幾關。曲線應該是鋸齒狀（緊張之後給喘息，再升高），一路單調上升會讓人疲勞，一直平的會無聊。新機制出現時，舊的壓力要先降下來。
- **心流的前提**：目標清不清楚、回饋是否即時（見第 4 節）、玩家是否覺得能掌控結果。
- **追上機制**：卡關時有什麼可以補（練等、換策略、動態難度）？補救是不是只有「刷」？

## 2. 隨機性：上癮還是挫折

- **用程式裡的機率算出來**，不要只憑感覺。
  - 單次機率 p，連續 n 次落空的機率是 `(1-p)^n`。
  - 最倒楣的 5% 玩家要嘗試 `ln(0.05)/ln(1-p)` 次才會中第一次。
  - 把這些數字寫進報告。例如 p = 5%，最倒楣的 5% 玩家要試 59 次以上。
- **隨機在行動之前還是之後**：
  - 行動前的隨機（input randomness，例如抽到的手牌、地圖）讓玩家去應對，產生策略。
  - 行動後的隨機（output randomness，例如命中率、掉寶）決定結果。結果越重要，越容易讓人覺得「不公平」。
- **挫折的訊號**：輸了以後，玩家說不出「是我哪裡沒做好」；連續倒楣沒有保底；隨機會吃掉很長的投入，例如一局 30 分鐘被一次骰子毀掉。
- **緩解手段**：保底（pity）、偽隨機（多次失敗後逐步提高機率）、讓玩家看得到機率、給重骰或改選的機會、讓結果小而頻繁而不是大而稀少。
- **上癮與倫理底線**：
  - 變動比率獎勵本身是遊戲樂趣的正常來源。
  - 以下情況算越線（dark pattern）：與真錢綁在一起、刻意製造「差一點就中」的假象、懲罰離線、機率不透明。報告要直接點名，標準與 `live-ops-designer` 的掠奪式付費標記一致。
  - 這一節與八角框架的驅力 7（不可預測）、8（損失與避免）互相引用，不要重複計分。

## 3. Loop：短期與長期怎麼搭配

| 層 | 時間尺度 | 例子 |
|---|---|---|
| 微 loop | 30 秒內 | 行動 → 回饋，本身就要好玩 |
| 核心 loop | 5–15 分鐘 | 一局、一場戰鬥、一個委託（目標 → 獎勵） |
| meta loop | 一個 session 以上 | 養成、解鎖、收集、劇情；要有自然的停點和回來的理由 |

逐層檢查：

- **是否形成閉環**：目標 → 行動 → 獎勵 → 投入 → 新目標。少了任何一環就是斷點，例如有獎勵但沒地方花。
- **內外層是否咬合**：內層的獎勵要餵進外層，外層要給內層新的理由去玩（新的敵人、build、規則）。外層只是把數字變大，內層很快會膩。
- **長期目標是否早點看得到**：第一個 session 結束前，玩家要能看到「之後能得到什麼」。
- **session 的開頭與結尾**：開頭多快能進入核心 loop？結尾有沒有讓人想回來的勾子（待領的獎勵、只差一點的進度）？
- 畫一張 loop 圖放進報告，用 ASCII，三層各一圈，畫出彼此怎麼連接。

## 4. 每個行動都有回饋

把第 2 步列出的動詞做成表格，**空著的格子就是一條發現**：

| 動詞 | 視覺 | 音效 | 震動 | 結果與進度 | 失敗時有沒有說明原因 |
|---|---|---|---|---|---|

- 「收到了」要在 100 ms 內出現，「結果」要在 0.5 秒內讀得懂（`game-designer` 的標準）。按下去沒反應，就算之後有結果，玩家也會以為沒按到。
- 回饋分三層：「收到了」（按鈕的按下狀態）、「發生了什麼」（命中、數字）、「我離目標更近了」（進度條、解鎖）。很多遊戲只做到第一層。
- 無效的操作也要回饋，例如錢不夠或還在冷卻，要告訴玩家為什麼不行。
- 音效同步與手感，在 headless 環境無法證明，表格裡標成「需實機」，不能寫成已驗證。

## 5. 八角框架（Octalysis）

8 個驅力各打 0–10 分，每個附一條證據：

| # | 驅力 | 帽 | 腦 |
|---|---|---|---|
| 1 | 使命感 Epic Meaning | 白 | — |
| 2 | 成就感 Accomplishment | 白 | 左（外在） |
| 3 | 創造力與回饋 Empowerment | 白 | 右（內在） |
| 4 | 擁有感 Ownership | — | 左 |
| 5 | 社交影響 Social Influence | — | 右 |
| 6 | 稀缺性 Scarcity | 黑 | 左 |
| 7 | 不可預測 Unpredictability | 黑 | 右 |
| 8 | 損失與避免 Avoidance | 黑 | — |

- **白帽與黑帽**：白帽讓玩家覺得自己變強、玩得有意義；黑帽讓玩家有急迫感，但累積下來會變成壓力。黑帽總分明顯高於白帽，就是「停不下來，但玩完不開心」，容易流失。
- **左腦與右腦**：左腦（外在獎勵）偏重時，獎勵一停玩家就走；右腦（內在樂趣）是長期留下來的原因。
- 單人原型的驅力 5 低分是正常的，寫明「不適用」就好，不用硬加社交功能。

## 6. 前期驗證：玩法與技術可行性

- **玩法原型**：
  - 有沒有用 placeholder（色塊、合成音、假文字）快速搭出可玩的版本？
  - README 有沒有寫要驗證的假設？
  - 通過條件能不能判定？例如「不操作會輸、高手會贏、試玩五次願意繼續」。
  - 結論是繼續、轉向還是放棄，有沒有寫下來？
- **順序**：正式美術、音樂、劇情是在玩法驗證**之後**才做嗎？先做美術再驗證玩法，要列為高風險。
- **技術風險**：列出這款遊戲最難的 3 個技術點，例如大量單位的效能、網頁版大小、手機觸控與 Safe Area、存檔、網路。檢查每一點：
  - 原型裡有沒有做過試作（spike）。
  - 有沒有量到數字（幀時間、MB、draw call）。
  - 只寫「應該可以」的算未驗證。
- 缺口用 Studio 的 `prototype` 補。

## 7. 設計文件涵蓋度：GDD、TDD、資源與時程

逐項標 **有／缺／過時**。「過時」是文件寫的和程式不一致，例如文件寫 12 個技能、程式只有 8 個。

| 類別 | 項目 | 夠具體的標準 |
|---|---|---|
| GDD | 核心玩法 | 一句話講得出玩家每分鐘在做什麼，loop 圖與第 3 節一致 |
| GDD | 美術、音效 | 風格有參考圖或 art bible；素材清單有數量 |
| GDD | 劇情 | 主線大綱、角色、劇情怎麼接進玩法 |
| 策劃 | 角色能力 | 每個角色有數值表，不是形容詞 |
| 策劃 | 戰鬥機制 | 傷害公式、命中與冷卻規則、勝負條件 |
| 策劃 | 技能數 | 確定的數字與清單，每個技能有用途，沒有完全重疊的 |
| 策劃 | AI 邏輯 | 每種敵人的行為規則（狀態或優先順序），玩家能讀懂並反制 |
| 策劃 | 關卡構建 | 關卡數、每關教什麼、難度曲線（接第 1 節） |
| TDD | 技術需求 | 引擎與版本、目標平台、效能預算、存檔與資料格式、第三方套件 |
| 規劃 | 資源與時程 | 素材與功能清單有工作量估計，里程碑有日期與驗收條件 |

- 原型階段不要求全部都有。標出**下一個里程碑之前必須補**的項目即可。
- 補文件用 Studio 的 `design-system`（單一系統的 GDD）、`quick-design`（小改動）、`create-architecture`、`architecture-decision`（TDD）、`asset-spec`、`estimate`、`sprint-plan`。

## 8. QA：能不能擋住壞版本

- **阻斷性缺陷**：當機、卡死無法前進、存檔遺失、無法開始或結束一局。列出已知的。有任何一個還開著，就不能發布。
- **流程打通**：從啟動、教學、核心 loop、結算或存檔，到重開讀檔，有沒有一條自動測試或 bot 跑完整條路？只測單一系統、沒有串起來的，算未打通。
- **兼容性測試**：
  - 列出目標平台，例如桌面瀏覽器、手機直式、iPhone Safari。
  - 實際測過哪些？匯出版和編輯器的行為常常不同（見 `prototypes/LESSONS.md`）。
  - 螢幕比例、Safe Area、觸控與滑鼠都要測到。
  - 沒有測過的平台寫「未測」。
- **回歸測試**：修過的 bug 有沒有對應的測試？README 有沒有寫清楚 L1／L2／L3 各跑哪些指令（見 repo 的 AGENTS.md「KISS 與分層測試驗收」）？
- 實際跑一次 README 的單元測試或冒煙測試，把結果寫進報告。跑不起來本身就是一條發現。
- 缺口用 Studio 的 `qa-plan`、`smoke-check`、`regression-suite`、`test-setup` 補。要判斷能不能進下一階段，用 `gate-check`。

## 報告

寫在該遊戲自己的資料夾，例如 `<遊戲>/reviews/YYYY-MM-DD-game-critic.md`，不要放在 repo 根目錄。結構：

1. **一句話總評**，加上各面向的分數表：A 五項、B 三項。
2. **最大的三個問題**：每個寫出玩家實際會遇到的情境，不寫抽象的術語。
3. **各面向的細節**：每條發現都附來源標籤。第 7 節的表格照抄並填上有／缺／過時。
4. **建議**：依「影響 × 成本」排序，每條包含：
   - 改什麼
   - 預期改善哪個面向
   - **改完怎麼驗證**：要跑哪個 bot 指標、算哪個數字，或請玩家觀察什麼。
5. **未量測**：還缺哪些證據，以及要用什麼方法取得。
